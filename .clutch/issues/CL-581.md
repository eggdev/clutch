# CL-581: Send the history of an eager group that a client did not name

## Goal

A client that gains an eager group holds each record of that group, also the records from before its last sync ID.

## Context

`Pull` in `packages/sync/runtime/server.server.ts` adds each eager group of the actor to the loaded set. `feed` in `packages/sync/service/feed.ts` then sends only the events after the client's last sync ID. A client at sync ID 500 that gains a new eager group never gets the records of that group from before 500, and its pool marks the group as loaded. A council review on 2026-11-20 found this.

The eager groups of the template are fixed: the organization and the user. So no screen shows the bug today. A project that adds an eager group, or a saved copy that lost its group list, meets it.

## Steps

1. Branch `clutch/cl-581-eager-history`.
2. Write the failing tests first: in `packages/sync/service/feed.test.ts`, and through the socket in `apps/api/src`.
3. When `lastSyncId` is above 0, `Pull` names each eager group that the client did not name in `groups`. The feed sends the backfill of those groups up to the last sync ID, before the backlog, as a `Load` does.
4. A client that reads pages gets the backfill in `Page` messages. `Pull` gets an optional `pages` key for that, so an older build still reads one message.

## Files

- `packages/sync/runtime/server.server.ts`, `packages/sync/service/feed.ts`
- `packages/sync/types/protocol.ts`, `packages/sync/runtime/transport.ts`
- `docs/contributing/architecture/local-first-sync.md`

## Acceptance criteria

- A client with a last sync ID above 0 that does not name an eager group gets the records of the group from before its last sync ID.
- The pool marks the group as loaded only once those records are in it.
- A client that names each eager group gets no backfill, as before.
- An older build that sends no `pages` key still gets the backfill, in one message.
