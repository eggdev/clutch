# CL-319: Take a captured ticket through Triage, Build and Deploy

## Goal

The owner says "log this" in any thread on the machine, and a ticket with enough information ends as a merged pull request with no more action from the owner.

## Context

This is the first slice that the owner can use. CL-317 adds the store and CL-318 adds the driver. This issue adds the three phases that need no owner: Triage, Build and Deploy. Planning and Design come in CL-320, and Review in CL-321. Until then, Triage holds a ticket that needs one of them.

### Capture

- Any agent runs `clutch tickets add "<title>" --description "<the owner's words>"`. For a ticket of another project, it runs the command in a checkout of that project.
- One line in the `AGENTS.md` that Clutch syncs tells each agent to do this when the owner says "log this", and to add `--hold` when the owner says "just log it".
- Capture starts no work in the thread that captured.

### Triage

Triage is the traffic controller. It runs in its own short thread and changes no code.

1. Read the ticket and the code it names.
2. Fill `kind`, `now`, `expected`, `location`, `acceptance` and `major` from the description and the code. Never guess a part that needs the owner's judgment.
3. Choose the route:
   - All 4 requirements are set (see CL-317): no `planning`.
   - The ticket changes nothing that a user sees, or it restores behavior that the owner approved before: no `design`.
   - Each other case keeps the phase.
4. Write the route and the reason with `tickets route`.
5. Until CL-320 merges: when the route needs `planning` or `design`, hold the ticket and give the reason.

### Build

Build is the first phase in the work thread, in a new worktree. It uses the `deliver` skill up to its "Verify and finalize" section. Its `check` is `mise exec -- bun run validate`. A change that passes the pull request size limit becomes more than one branch, in order.

### Deploy

Deploy opens the pull requests, stays with them and merges them. The hosting platform deploys on the merge to `main`. Clutch runs no deploy script.

- One ticket can have more than one pull request. They always form one `gh stack`: `pr open --base` links them, and `pr merge <top>` merges from the bottom up.
- The `babysit-pr` skill watches each pull request of the stack, not only the top one.
- `pr open` links each pull request to the ticket with `tickets link`.
- The `check` of the phase passes when each linked pull request is merged. So a ticket is done when its whole stack is on `main`.
- A major change waits for the owner, as the merge judge already decides (`tools/github/major-change.ts`).
- After `done`, the worktree and its local branches are removed.

## Steps

1. Branch `clutch/cl-319-first-phases`.
2. Write the `triage`, `build` and `deploy` entries of the default `.clutch/phases.yaml`, with their prompts.
3. Add the capture line to `AGENTS.md`.
4. Find each place where `pr open`, `pr merge` and the checks need an issue file for the branch. Make each one accept a branch of a ticket, and commit no issue file for it.
5. Make `pr babysit` plan its round over each pull request of the stack. Update the `babysit-pr` skill.
6. Remove the worktree after the last merge. Check that `clutch worktree prune` finds a worktree that T3 Code made.
7. Hand test: log one small real ticket in Clutch and follow it to the merge.

## Acceptance criteria

- After `tickets add` with a full bug report, the ticket has a route with no `planning` and no `design`, and a Build thread runs in a new worktree.
- After `tickets add` with one vague sentence, the ticket is held with a reason, and no Build thread starts.
- `pr open` on a ticket branch opens a pull request, links it to the ticket and commits no file in `.clutch/issues`.
- A ticket with 2 pull requests has them in one `gh stack`, and a red check on the bottom one starts a babysit round.
- `tickets phase <id> deploy done` exits 1 while a linked pull request is open.
- After the merge, `tickets show <id>` shows each phase as `done`, and the worktree is gone.

## Decisions

The coordinator made these changes after CL-318.

- The issue splits in two. [CL-319a](./CL-319a.md) changes the phase file and the driver. This issue changes the pull request tooling on top of it. The hand test in step 7 runs after both merge.
- `.clutch/phases.yaml` has a `command` key: how an agent runs Clutch in the project. In Clutch it is `mise exec -- bun run clutch`. The prompt of each phase uses it.
- `t3 thread start --json` prints no worktree, and `t3 thread show --json` can still give an empty path right after the start. So when a ticket has no `worktree` link at `done`, `done` asks the work thread again before the `check` runs.
- `pr merge <top>` on a stack needs `--owner`, and only the owner can allow that. So Deploy merges the pull requests of the stack one at a time, from the bottom up, each with `pr merge <number>` and no `--owner`. When `pr merge` cannot merge, Deploy sets the phase to `blocked` with the output as the reason. CL-325 makes the merge judge run on the machine.
- A ticket id has 4 or more digits, such as `CL-1000`, and an issue id has 3. The parsers of a branch name tell the two apart. A ticket branch commits no issue file.
- The `check` gets the ticket id in `CLUTCH_TICKET`. `tickets merged <id>` is the check of Deploy. It exits 1 when the ticket has no `pull_request` link.
- `dispatch` removes the worktree of a finished ticket, because the agent runs `done` from inside it. It keeps a worktree with uncommitted changes, and the one that the dispatch runs in.
- Triage runs on `claude-sonnet-5-5`. The work thread keeps `claude-opus-5-5`.
- `tickets hold --reason` keeps the reason of a hold, and `release` clears it. The store moves to version 2, and a store of version 1 opens with no reasons.
