# CL-575: Keep each waiting transaction in its own row, so two tabs do not erase each other's work

## Goal

Two tabs of one person on one device never erase each other's waiting transactions or loaded records from the local database.

## Context

The local database holds the whole pool state under one key: `packages/sync/runtime/indexed-db.ts` on the web, and one JSON row in `packages/sync/runtime/sqlite.ts` on native. Each tab has its own pool, and `save` in `packages/sync/runtime/boot.ts` writes the whole snapshot of that pool. A council review on 2026-11-20 found two results.

- Tab A makes a change offline and saves it. Tab B gets a delta and saves its own state, which has no waiting transaction. When tab A closes before it connects again, the change is lost.
- Each change writes every record again, so the cost of one save grows with the number of records on the device. Linear writes only the changed rows, with the sync position in the same database transaction.

A change of the layout later needs a path for the copies that devices hold then, so this comes before a project has many records.

## Steps

1. Branch `clutch/cl-575-rows-in-local-database`.
2. Write the failing case first, in `packages/sync/testing/local-database-conformance.ts`: two pools on one database, and a waiting transaction of one survives a save of the other.
3. Change the seam in `packages/sync/types/local-database.ts`: one row for each record, one row for each waiting transaction, and one row for the sync position and the loaded groups.
4. Write the changed records and the sync position in one database transaction. A tab adds and deletes only its own waiting transactions.
5. Decide how a second tab learns of a transaction that the first tab made. The server already applies a transaction once.
6. Read a copy in the old layout once, or drop it and load again from the server.

## Acceptance criteria

- A waiting transaction of one tab is in the local database after a save of another tab.
- One delta writes only the records that it changed, with the sync position, in one database transaction.
- Both adapters pass the same conformance cases.
