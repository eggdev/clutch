# CL-325: Run the merge judge and the release on the machine without GitHub Actions

## Goal

A routine pull request merges with no action from the owner when its checks pass, and each merge to `main` is released, while GitHub Actions is off.

## Context

GitHub Actions is off on the owner's repositories. Local CI runs the checks of each pull request on the machine. Three things still need Actions, and none of them works now.

- **The merge judge.** `pr merge <number>` starts the `Auto-merge` workflow and waits for it. On 2026-11-21 the run for #334 stayed queued with no jobs, and `pr merge` gave up. So a pull request merges only with `--owner`, which needs the owner's word each time.
- **The release.** `release.yml` runs on a push to `main`. The last release is v1.26.7, from 2026-11-20 at 19:39 UTC. Pull requests #330 to #333 merged after it and are not released. So the other projects cannot sync them.
- **The release bot opens no pull request.** `pr open` waits 3 minutes for `open-pr.yml`, then opens the pull request as the owner. So the owner cannot approve it on GitHub.

The ticket workflow depends on the first one. The Deploy phase of CL-319 merges with `pr merge`, and the owner decided that routine work merges without the owner.

### What the owner must decide

The bot's key is in the `release` environment of GitHub today, so only a workflow on the default branch can use it. To run the judge and the release on the machine, the key must be readable on the machine.

- **Option 1: the key moves to 1Password.** The machine reads it with the service account of the project, as it reads other secrets. Local CI runs the judge when the checks of a pull request pass, merges with the bot's token, and runs the release for each new commit on `main`.
- **Option 2: no bot.** The machine merges and releases with the owner's own token. The judge still decides. Bot-opened pull requests and owner approval on GitHub stop.
- **Option 3: turn GitHub Actions on again** for these three workflows only.

The agent's pick is option 1. It keeps the judge and the approval flow as they are, and it uses the secret store that the projects already use.

## Steps

1. Ask the owner to choose an option. Do not start before the answer.
2. List what `auto-merge.yml`, `release.yml` and `open-pr.yml` do, step by step, and the secrets that each one needs.
3. Make the judge runnable as a command on the machine. Its rules stay in `tools/github/auto-merge.ts`.
4. Make local CI, or `pr merge` itself, run the judge and the release.
5. Make `pr merge` on a stack merge from the bottom up through the judge, one pull request at a time, with no `--owner`.
6. Release the commits on `main` that have no release.

## Acceptance criteria

- With GitHub Actions off, `pr merge <number>` on a green routine pull request merges it, and no person acts.
- A major change still waits for the owner's approval.
- `pr merge <top>` on a green stack of 3 merges all 3 from the bottom up, with no `--owner`.
- After a merge to `main`, a new version tag exists within 10 minutes.
- No secret is written to a file in a repository or to a log.

## Verify

- `mise exec -- bun test tools/github apps/local-ci`
- `mise exec -- bun run validate`
- One real routine pull request in Clutch merges and is released with no action from the owner.
