# CL-596: Run the native journeys in local CI on a pool device

## Goal

The local CI service runs the native journeys of a pull request that reaches native, on one device of the shared pool, with no T3 Code tools.

## Context

The owner asked for this on 2026-11-21, after CL-497 removed the GitHub Actions native jobs. A CI job has no `device_open`, so it takes its own lease from Simlock, the pool's leasing daemon. The pool's address and its token are settings of the machine, as the build machine is. The same `AGENT_DEVICE` contract serves both callers. CI must not starve agents: the pool runs 3 devices.

## Design

The facts come from `simlock instructions` (Simlock 0.8.0) and the Simlock docs, read on 2026-11-21.

1. **One job.** `.github/workflows/ci.yml` gets a `native` job, and local CI runs it in its Linux container. Its first step runs `tools/journeys/reach.ts`. When the change does not reach iOS, each later step is skipped, so the job passes at once and takes no lease.
2. **The lease.** Simlock's own route for a remote caller is `agent-device`: set `AGENT_DEVICE_DAEMON_AUTH_TOKEN` to an agent token, run `agent-device connect proxy --daemon-base-url <pool URL>/v1/agent-device` once, then `agent-device open --platform ios --device "iPhone 17"` with a session name of the job. `open` takes the lease and waits in Simlock's queue. `agent-device close` gives the device back. No code of this repository calls the Simlock HTTP API.
3. **The contract.** A small script, `tools/native/with-device.ts`, does the steps of point 2, writes a wrapper command that holds the session name, puts its path in `AGENT_DEVICE`, runs the command that it is given, and always closes the device: at the end, on a failure and on a stop signal. So `native:build --install` and `journey --native ios` run in CI as they run in an agent session.
4. **A job that dies.** A container that local CI kills cannot close its device. Simlock ends a lease that nobody renews when its time is over, 15 minutes by default, and deletes the device.
5. **One device for CI.** CI gets a token of its own. Simlock gives one requester one lease by default (`lease.maxPerRequester`), so CI can never hold 2 devices. A second native job at the same moment would be refused with `REQUESTER_ALREADY_LEASED`, so local CI also gets a limit for one check: at most 1 `native` job at a time, and the next one waits for its slot.
6. **The build and the dev servers.** The job needs the build machine as an agent does: it copies the build of the fingerprint from it, makes one there when none exists, and forwards the port of its dev proxy to it. So the job needs an ssh key for the build machine. The job starts its dev servers on another proxy port than 1355, so it never takes the port of an agent session on the same machine.
7. **The merge rule.** `tools/github/auto-merge.ts` reads the checks `native-ios` and `native-android`. It reads `native` from then on.

## Steps

1. The owner creates what the Blocked section lists.
2. Add `tools/native/with-device.ts` with tests that use a fake command, and prove it against the pool with the CI token.
3. Add the limit of one check to `apps/local-ci`.
4. Add the `native` job, and name its secrets and variables in `apps/local-ci/README.md`.
5. Point the merge rule and `.agents/skills/deliver/references/pull-requests.md` to the `native` check.
6. The owner adds `native` to `checks` in the local CI config.

## Acceptance criteria

- C1: A pull request that reaches native gets a `native` status from local CI, from a run on a pool device.
- C2: A pull request that does not reach native starts no lease.
- C3: A job that fails or is cancelled ends its lease.
- C4: Two native jobs never hold two devices at once.

## Verify

Read the `native` status and its log on a pull request that changes `apps/app`.

## Blocked

The job needs 2 new credentials and 3 addresses. An agent does not create a credential. The owner creates each one and puts it in the 1Password Environment of the repository (`op_environment` in the local CI config), or in the `.env` file beside its token:

1. `SIMLOCK_TOKEN`: a Simlock token of role `agent` for CI only. On the pool machine: `simlock token create --role agent --label local-ci`. The secret shows once.
2. `SIMLOCK_URL`: the HTTPS address of the pool, with no `/v1`. It is the address that T3 Code's device host of kind `simlock` uses.
3. `BUILD_MACHINE_SSH_KEY`: a new ssh private key for CI, with its public key in `authorized_keys` of the build user on the build machine. `BUILD_MACHINE_KNOWN_HOSTS`: the host key line of the build machine.
4. `BUILD_MACHINE_SSH` and `BUILD_MACHINE_ROOT`: the two values of `~/.config/clutch/build-machine.json`, with an address that a job container can resolve.

Two facts are not proven and need the token: whether a job container reaches the pool's address and the build machine (a container has its own name lookup), and the exact output of `agent-device connect proxy` on Linux. Step 2 proves both before the job is written.

The owner also decides one thing: a token of role `agent` and an ssh key both let a CI job run commands on the pool machine. Local CI runs only pull requests of authors on its allowlist, in a container that mounts nothing.

Unblock: the 4 items exist, and the owner says so in this issue.
