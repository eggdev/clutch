# CL-440: Ship the core journey catalog that every project verifies

## Goal

Clutch ships one catalog of core journeys that every product needs, each with the proof that it works. A project adopts the catalog at kickoff and adds its own core features.

## Context

- `docs/principles/proof-gates-code.md` names the core journeys: sign-up, sign-in, onboarding, profile management, billing and checkout, roles and access, account security, and contact support.
- On Neighborhood, sign-in on web and iOS, app start, a second project and the Workspace broke with every check green. A seed gave the test account a paid plan, so no test saw the free plan that real users have. An agent opened a route directly, so no test saw that no button led to it.
- `docs/contributing/project-intent.md` lists a project's hard invariants and their journeys. The journey header is in `.agents/skills/setup-verification/references/journey-specification.md`. `tools/check-journeys.ts` checks each header.

## Steps

1. Add `docs/contributing/journeys/core.md`, with one section per core journey:
   - The outcome that must be true, as an assertion.
   - The user: a new account on the free plan, on a mid-range phone.
   - The entry: the first screen a new user sees. A direct route does not count.
   - The budgets: clicks to finish (sign-up in 3 or fewer), no layout shift, no accessibility error.
   - The vendor in test mode: the email inbox, and the payment provider's test cards and test clocks.
   - The failure states it also proves: a wrong password, a declined card, a refused role.
2. Add a journey template for each core journey to `.agents/skills/setup-verification/references/`.
3. Make kickoff record in `clutch.yaml` which core journeys the project has, with a reason for each that it leaves out. Make `clutch doctor` check that each one it has has a journey.
4. Add a `budgets:` block to the `clutch.yaml` schema, which kickoff fills: the layout shift limit (default 0.01), the clicks or taps for each core journey (sign-up default 3), and the time to value (first screen to the activation event). CL-442 and CL-446 read it.
5. Add `Core:` to the journey header, naming the catalog entry that the journey proves.
6. Make `tools/check-journeys.ts` reject a `Core:` journey that does not hold to the catalog:
   - it opens more than one URL, or a URL other than the entry
   - it loads a seed fixture or a seeded account
   - it does not create its account through the sign-up screens
7. In `setup-verification`, add the step that reads the project's PostHog recordings of a flow through the PostHog API, when the project has PostHog. The agent adds the real order, devices and detours as journey steps. A project without PostHog skips the step.

## Files

- `docs/contributing/journeys/core.md`
- `.agents/skills/setup-verification/` and its references
- `.agents/skills/kickoff/SKILL.md`
- `tools/check-journeys.ts` and its test
- `apps/cli/src/doctor/` and the `clutch.yaml` schema

## Acceptance criteria

- Each core journey has an outcome, a user, an entry, budgets, test-mode vendors and failure states.
- `clutch doctor --check` fails for a core journey that the project has and that has no journey.
- `check-journeys` fails a `Core:` journey that opens a second URL, uses a seeded account, or skips sign-up.
- `bun run validate` passes.

## Verify

`mise exec -- bun run validate`. Run `clutch doctor --check` in a scratch project that drops its sign-in journey, and see it fail.
