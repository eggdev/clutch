# CL-919: Tie the local database to its user, and stop the old engine when a session ends

## Goal

One person never sees or sends the saved work of another person on the same device.

## Context

A council review on 2026-11-20 found three gaps around the end of a session. The identity of the template is a development stub, so no screen shows them yet.

- `apps/app/lib/boot.ts` opens the local database with the fixed name `app`, and a saved transaction names no actor. When a session ends with no 4401 close, such as offline or by an expired cookie, the next person on the device boots with the records and the waiting transactions of the last one. `Push` then settles those transactions as the new actor.
- No production code calls `Sessions.end`, and no server path fails `Pull` with `SessionEnded`. A client that was offline when its session ended never learns it.
- `onSessionEnded` clears the database and starts the app again, but the old engine and its save listener keep running. On native, where no page reloads, a later change of the old pool writes its old state back over the cleared database. CL-574 stops the engine of an ended session, so no delta does this any more. A change that the person makes on the old screen while the database clears still does.

Linear clears the local database on sign-out. Its study also says to decide which record types a device may hold.

Trigger: a project adds its real identity provider.

## Steps

1. Branch `clutch/cl-919-local-database-per-user`.
2. Name the local database by its user, or save the user with the state and drop a copy of another user at boot.
3. Stop the engine and the save of the old pool before the database is cleared.
4. Refuse the socket of an ended session in a way that the client reads as an ended session, also after it was offline.
5. Clear the local database on a sign-out that happens offline.

## Files

- `apps/app/lib/boot.ts`, `packages/sync/runtime/boot.ts`, `packages/sync/runtime/transport.ts`
- `packages/sync/runtime/server.server.ts`, `packages/identity/`

## Acceptance criteria

- A second user on one device boots with none of the records and none of the waiting transactions of the first.
- After a session ends, no write of the old pool reaches the local database.
- A client that was offline when its session ended clears its local database when it connects.
