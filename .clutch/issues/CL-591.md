# CL-591: Keep the proof of an applied transaction past the trim, and cap a push

## Goal

A transaction applies once, also when its client sends it again after the trim deleted its event. The server refuses a `Push` of more than 100 transactions.

## Context

The review of 2026-11-20 found both by reading.

`findTransaction` in `packages/sync/repo/events.ts` finds a transaction by its event. The trim in `packages/sync/repo/trim.ts` deletes old events. A device whose push was accepted, and whose tab closed before the delta came, keeps the transaction as waiting. When it stays away longer than `SYNC_LOG_KEEP_DAYS`, the trim deletes the event. Its next pull gets `ServerBehind`, the client sends each waiting transaction again, `findTransaction` finds nothing, and the change applies a second time.

The client sends at most `transactionsPerPush` (100) transactions in one `Push`, but the server takes any number.

## Steps

1. Branch `clutch/cl-591-applied-transactions`, stacked on CL-590.
2. Write the tests first: a transaction sent again after the trim deleted its event gets its first sync ID and makes no second event; a `Push` of 101 transactions over the real socket is refused and applies none.
3. Add the table `sync_transactions` (organization, transaction ID, sync ID, time). The trim moves the transaction ID of each event that it deletes into it, in the same statement. `findTransaction` looks in the log and in that table.
4. `Push` refuses a list longer than `transactionsPerPush` before it runs any transaction.
5. Say how long the rows stay, and what one costs, in `server.md`, `local-first-sync.md` and `data-storage.md`.

## Acceptance criteria

- A transaction whose event the trim deleted gets the accepted outcome with its first sync ID, and no second change, when it is sent again.
- The migration adds a table only.
- A `Push` of more than 100 transactions applies none of them. A client of this repository never sends one.
