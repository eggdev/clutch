# CL-318: Start a thread when a phase of a ticket is ready

## Goal

A phase that becomes ready starts its agent thread in T3 Code with no action from the owner, and the machine never runs more threads than its limits allow.

## Context

CL-317 adds the store. This issue adds the phase file and the driver. The owner chose the most basic driver: no webhook and no service. The Clutch CLI starts the thread itself. The events keep the webhook shape, so a webhook task can replace the driver later.

### The phase file

`.clutch/phases.yaml` defines the phases. Clutch ships a default, and a project owns its copy after the first sync (`seed` with `add_on_sync` in `clutch.files.yaml`).

```yaml
schemaVersion: 1
limits:
  threads: 6 # work threads that run at once on this machine
  device: 2 # phases that need a device, at once
work_thread:
  provider: claudeAgent
  model: claude-opus-5-5
phases:
  - id: build
    thread: work # work: the one work thread of the ticket. own: a thread of its own.
    skills: [deliver]
    prompt: 'Build the ticket in this worktree.'
    check: 'mise exec -- bun run validate'
    needs: []
    advance: agent # agent | owner
    statuses:
      blocked:
        prompt: 'Write the question for the owner in the ask-the-owner form, then stop.'
```

- `thread: own` starts a new thread for the phase, with the `provider` and `model` of the phase. Triage and Planning use it.
- `thread: work` uses the one work thread of the ticket. The first such phase starts it in a new worktree from `origin/main`. Each later phase sends its prompt to the same thread. T3 Code sets the model when a thread starts, so all work phases share `work_thread`.
- `skills` and `prompt` exist for the phase, and again under `statuses` for each status. The driver sends a status prompt when the phase enters that status.
- `check` is a command. `tickets phase <id> <phase> done` runs it in the worktree of the ticket and refuses `done` when it fails.
- `needs` names what the phase uses: `device` or `dev_stack`. A phase that needs a device counts against `limits.device`.
- `advance: owner` means that `done` needs `--approved-by owner --quote <the owner's words>`. The quote goes in the event.

The owner said that the limit is the machine, local CI and the device pool, not a fixed count of builds. So `limits.threads` is one number for the machine that the owner tunes. Local CI queues its own jobs. The device pool allows 2 leases.

### The driver

`tickets dispatch` runs at the end of each command that writes, and by hand.

1. Find each phase row that is `ready`, on a ticket that is not held and whose dependencies are done.
2. Skip a row when its start would pass a limit.
3. Claim the row. Then start its thread:
   - A new thread: `t3 thread start --json --title "<id> <phase>: <title>" --provider <p> --model <m> [--worktree origin/main --branch clutch/<id>-<slug>] <project> <prompt>`.
   - The work thread of the ticket: `t3 thread send <thread> <prompt>`.
4. Save the thread id on the phase row.
5. When the start fails, set the row back to `ready` and record the error. The next dispatch tries again.

The prompt is the prompt of the phase, the names of its skills, and one line that tells the agent to read the ticket with `clutch tickets show <id>` and to end with `clutch tickets phase <id> <phase> done`.

Each start, each skip for a limit and each failure writes one JSON line to `~/.local/state/clutch/<project>/dispatch.jsonl`. The nightly backup covers that folder.

## Steps

1. Branch `clutch/cl-318-ticket-driver`.
2. Add the reader and the checks of `.clutch/phases.yaml`. Add `tickets phases --check`. It fails on an unknown key, an unknown phase, or a skill that is not installed for the agent.
3. Add `tickets dispatch`, and call it after each write.
4. Make `tickets phase ... done` run `check` and honor `advance`.
5. Send the status prompt when a phase enters a status that has one.
6. Test the driver with a fake `t3` command on the path.
7. Add the file to `clutch.files.yaml` and document it in `.clutch/README.md`.

## Acceptance criteria

- With a fake `t3`, `tickets add` causes one `t3 thread start` call. A second `tickets dispatch` causes no call.
- With `limits.threads: 1` and two ready work phases, one thread starts. The second starts after the first ticket is done.
- With `limits.device: 2`, a third phase that needs a device stays `ready`.
- The second work phase of a ticket causes `t3 thread send` to the thread that the first one saved.
- `tickets phase <id> build done` exits 1 and keeps the status when `check` fails.
- `done` on a phase with `advance: owner` exits 1 without `--approved-by owner`.
- When `t3` fails, the phase is `ready` again and the log has one line with the error.
- `tickets phases --check` exits 1 on a phase file that names a skill that is not installed.

## Verify

## Decisions

- Each record that a write changes gets its own event, so `done` also writes the event of the next phase that becomes `ready`. A new phase row gets a `create` event.
- A ready phase with no entry in the phase file stays ready, and dispatch logs a skip. The default file has only the `build` entry. CL-319 adds the other entries.
- `t3 thread start --json` prints only `threadId`, `projectId` and `runId`. So the driver reads the worktree with `t3 thread show --json` and links it to the ticket. `check` runs there, or in the current folder when the ticket has no worktree link.
