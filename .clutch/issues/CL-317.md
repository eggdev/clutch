# CL-317: Keep tickets in one store that every worktree of a project shares

## Goal

Every agent on the machine sees the same ticket state at once, and two agents never take the same phase of a ticket.

## Context

The owner agreed this design on 2026-11-21. It replaces the draft that used the id CL-315. This issue adds the store and its commands. CL-318 adds the driver that starts threads. CL-319 makes the first three phases work from capture to merge.

The Markdown files in `.clutch/issues` and the `clutch issues` command do not change. The store is a new command group, `clutch tickets`. No import exists. The owner does not need one now.

### The store

- Each project has its own store. No store holds more than one project.
- The store is one SQLite file at `<git-common-dir>/clutch/tickets.sqlite`. Every worktree of the project shares it, and git does not track it.
- No server and no daemon runs. The Clutch CLI opens the file for each command. Bun includes SQLite.
- The Clutch CLI is the only reader and the only writer. Agents and tools use the commands, never the file.

### The ticket

One record type serves the inbox and the work. An inbox item is a ticket that has no route yet, so it keeps its id from capture.

- Identity: `id`, `title`, `description`, `kind` (`bug`, `feature` or `chore`), `source` (the thread that captured it). No command changes `description`. It holds the words of the owner.
- Requirements: `now`, `expected`, `location`, `acceptance` (a list of checks), `major` (yes or no).
- Route: `route` (the ordered list of phases), `route_reason`, `hold`.
- Plan: `body` (Markdown), and one `depends_on` row for each dependency.
- Links: one row for each link, with a kind: `prototype`, `pull_request`, `branch`, `worktree` or `evidence`.
- The id is `<prefix>-<number>`. The prefix is `tickets.prefix` in `clutch.yaml`. Numbers start at 1000, so no ticket id equals the id of an old issue.

### The phase rows

A ticket has one row for each phase on its route: `phase`, `status`, `claimed_by`, `thread`, `blocked_reason`, `started_at`, `finished_at`.

- The phases are `triage`, `planning`, `design`, `build`, `review` and `deploy`.
- The statuses are `not_ready`, `ready`, `in_progress`, `blocked`, `in_review` and `done`.
- A new ticket has one row, `triage`. Its status is `ready`, or `not_ready` when the ticket is held.
- `done` in one phase sets the next phase on the route to `ready`.
- When an earlier phase goes back to `ready`, every later phase goes to `not_ready`.
- The claim is on the phase row, so each phase records the thread that did it.

### The rule for a route with no Planning

`tickets route` refuses a route that has no `planning` phase unless all of these are true. It prints the parts that are missing.

1. `now` and `expected` are set.
2. `location` is set.
3. `acceptance` has at least one check.
4. `major` is no.

### The events

Each change writes one row in `events`, in the same transaction. The shape follows the Linear webhook that the owner used before, so a webhook task of T3 Code can filter on it later.

```json
{
  "deliveryId": "<uuid>",
  "createdAt": "<ISO time>",
  "actor": "<name or thread>",
  "type": "Phase",
  "action": "update",
  "data": { "id": "CL-1000", "phase": "build", "status": "ready" },
  "updatedFrom": { "status": "not_ready" }
}
```

`type` is `Ticket` or `Phase`. `action` is `create` or `update`. `data` holds the record after the change. `updatedFrom` holds the old value of each changed field.

### The commands

Every command prints JSON with the `schemaVersion` field.

- `tickets add <title> --description <text> [--kind <kind>] [--hold]`
- `tickets list [--inbox] [--phase <phase>] [--status <status>]`, `tickets show <id>`, `tickets ready`
- `tickets edit <id>` with `--now`, `--expected`, `--location`, `--acceptance` (repeatable), `--major`, `--kind`, `--depends` and `--body-file`
- `tickets route <id> --phases <list> --reason <text>`
- `tickets hold <id>` and `tickets release <id>`
- `tickets claim <id> <phase> --as <name> [--thread <thread>]`: one transaction sets `in_progress` and the claim. A second claim of the same phase fails with exit 1.
- `tickets phase <id> <phase> <status> [--reason <text>]`
- `tickets link <id> --kind <kind> <value>`
- `tickets events [--ticket <id>] [--since <event number>]`

## Steps

1. Branch `clutch/cl-317-ticket-store`.
2. Add `apps/cli/src/tickets/store.ts`: open the file in the git common directory, make the tables, and run each write in an immediate transaction that also writes the event.
3. Add the commands, and register `tickets` in `apps/cli/src/commands.ts`.
4. Take a new id from the store inside the transaction that inserts the ticket.
5. Test a claim race: 20 processes claim one phase, and 1 wins.
6. Add a "Tickets" section to `.clutch/README.md` that documents the store and the commands.

## Acceptance criteria

- A ticket added in one worktree shows in `tickets show <id>` in another worktree of the same project, with no commit.
- When 20 processes claim one phase at the same time, 1 exits 0 and 19 exit 1.
- `tickets add --hold` makes a ticket whose `triage` phase is `not_ready`. `tickets release` sets it to `ready`.
- `tickets route` with no `planning` phase exits 1 and names each missing requirement. With the 4 requirements set, it exits 0.
- `tickets phase <id> build done` sets the next phase on the route to `ready`.
- Each write adds exactly one event with `deliveryId`, `type`, `action`, `data` and `updatedFrom`.
- Two projects on one machine have two store files, and no command of one reads the other.
- `clutch issues` prints the same output as before this change.
