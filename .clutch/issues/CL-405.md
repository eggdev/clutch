# CL-405: HUMAN GATE: Turn on the merge queue and auto-merge

## Goal

Brendan turns on the merge queue and `allow_auto_merge`, and switches `automerge.mode` to `on`.

## Gate

Repo settings, and merges to main without Brendan, need his explicit approval.

## Steps (agent)

1. Summarize the dry-run results from CL-404: count, false positives and misses.
2. Ask Brendan in the PR, in this order, with the settings commands:
   1. Confirm the CL-106 ruleset is on for `main`.
   2. Add a bypass for the GitHub Actions bot. `release.yml` pushes the release commit to `main`.
   3. Turn on the merge queue in the ruleset, with the merge-commit method.
   4. Turn on allow auto-merge in the repository settings.
   5. Approve the one-line PR that sets `automerge.mode: on`.
3. In the same PR, give the `decide` job in `.github/workflows/auto-merge.yml` `contents: write`. `gh pr merge --auto` needs it, and the dry run ships with `pull-requests: write` only.
4. In the same PR, merge with the release bot token, not `GITHUB_TOKEN`. Mint it with `actions/create-github-app-token`, pinned like the other workflows, from `CLUTCH_APP_ID` and `CLUTCH_APP_PRIVATE_KEY`, and pass it as `GH_TOKEN` to the merge. A merge made with `GITHUB_TOKEN` starts no workflow, so the release workflow and CI on `main` would not run after an auto-merge. Brendan approved the GitHub App approach on 2026-10-30.

## Decisions needed before enabling

- `bun run pr merge` (`tools/github/pr.ts`) is not queue-aware. With a queue, it returns before the merge lands, so `clutch issues set ... done` would run early. Make it queue-aware first.
- Decide how stacks merge with a queue. A queue takes only PRs whose base is `main`.
- A release commit moves `main` under the queued entries. Decide whether the queue rebases them, or whether `release.yml` waits for the queue to drain.

## Acceptance criteria

- The `merge_queue` and `allow_auto_merge` remote probes pass (`apps/cli/src/doctor/remote.ts`), and `risk_tier_automerge` is adopted.
