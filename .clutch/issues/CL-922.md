# CL-922: Harden the copies of the queue of a lost local database

## Goal

A tab that loses its local database keeps its waiting transactions in each order of events.

## Context

A tab writes its queue of waiting transactions to `localStorage` before it lets its database go, and the next open writes the copies back (`packages/sync/runtime/indexed-db-copies.ts`, `boot.ts`). The seventh round of the council review, on 2026-11-20, gave the sync engine 9/10 and left these on the list for later. Each needs a rare mix of events.

- When the database has no generation yet, `writeBack` takes the generation of the copy whose key sorts first. After a rebuild, a copy of an older session can then win, and the waiting transactions of the current session are dropped. A probe in Chromium confirmed the order. The simplest fix: the rebuild writes its generation into the new database before the copies are written back.
- `followLostDatabase` writes the same copy twice. When another tab writes the copies back between the two, the second copy stays, and a later open brings back rows that the server confirmed in the meantime. The server applies a transaction once, so the local change shows only for a moment.
- When a rebuild fails after the delete, the handle keeps a closed connection. Each later save fails, `onLost` never wakes, and the queue is not kept.
- The `blocking` handler wakes its listeners before it closes the connection. A listener that throws leaves the connection open.
- The module with this code loads after the first screen. A device that is offline without the module in the store of the service worker cannot open a database that has a copy.
- When `localStorage` is full, no copy is kept.
- The tests of `packages/sync` took 59 of their 60 seconds on a loaded machine, and about 34 on a quiet one.

Trigger: the first project that ships to devices with little storage, or the first report of a lost waiting transaction.

## Steps

1. Branch `clutch/cl-922-queue-copies`.
2. Write a failing test for each case, in `packages/sync/runtime/indexed-db-keep.browser.test.ts`.
3. Fix each case, one commit for each.
4. Give the race tests their own target, or shorten them, so the budget has room.

## Files

- `packages/sync/runtime/indexed-db-copies.ts`, `indexed-db.ts`, `boot.ts`
- `packages/sync/runtime/indexed-db-keep.browser.test.ts`

## Acceptance criteria

- After a rebuild, the waiting transactions of the current session are in the queue, whatever the keys of the copies are.
- A row that the server confirmed does not come back from a copy.
- A rebuild that fails keeps the queue, and the tab starts again.
- The tests of `packages/sync` take under 45 seconds on a loaded machine.
