# CL-484: Start the iOS lane of CI only where a repository turns it on

## Goal

CI starts the `native-ios` job only in a repository that turns the iOS lane on. CI on `main` ends green in a repository that does not.

## Context

- The `native-ios` job runs on a GitHub macOS runner. On 2026-11-12 each run reached the native build and was cancelled at the limit of 25 minutes.
- A cancelled job makes the whole CI run `cancelled`. So no CI run on `main` ended `success` after 2026-11-12.
- The Deploy workflow starts only after a CI run on `main` that ended `success`. It was skipped each time.
- The `rejudge` job of Auto-merge starts on the same event. It did not start either.
- The merge judge holds a pull request whose `native-ios` job failed, was cancelled or still runs. The owner's approval does not lift that hold. A skipped job holds nothing.
- The owner decided on 2026-11-13 to turn the job off on GitHub first. He chooses the place of the iOS builds as a second step.
- CL-469 and CL-471 describe an iOS lane that can pass and that the judge requires.

## Steps

1. Branch `clutch/cl-484-ios-lane-opt-in`.
2. In `.github/workflows/ci.yml`, start `native-ios` only when the repository variable `CLUTCH_IOS_LANE` is `on`.
3. Leave `tools/journeys/reach.ts` as it is. The reach rule says which platforms a change reaches. The variable says whether this repository has an iOS lane in CI.
4. Move the two pages that state when the job runs.

## Files

- `.github/workflows/ci.yml`
- `docs/contributing/end-to-end-testing.md`, `docs/contributing/setup/native.md`

## Acceptance criteria

- With no `CLUTCH_IOS_LANE` variable, a pull request that reaches iOS has a skipped `native-ios` job.
- The CI run of the merge commit on `main` ends `success`.
- The Deploy workflow starts after that run.
- With the variable set to `on`, the job starts as before.

## Verify

- `mise exec -- bun run validate`
- The CI run and the Deploy run of the merge commit on `main`.
