# CL-410: Propose a design before building a new screen, and keep the adopted one as the spec

## Goal

Give agents one way to design a screen before they build it, and to keep the
build true to the design. In Brendan's words: "We just need a mechanism for
designing something, and for keeping the designs true through the build."

## Context

The 75-repo design study (Oct 2026) found that design lives in code and in
agent skills, not in a separate tool. The clearest pipelines: paperclip's
`directions-lab` (today plus 2 or 3 directions, proposed, adopted, current,
historical), lobehub's `design-prototype` (a prototype on the real UI runtime
and tokens, so promotion is a file split), n8n's spec before implementation
and an experiments skill from create to retire, and OpenHands' design doc that
feeds a screenshot gate. Lane E builds the prefer-primitives lint rule (CL-406)
and the screenshot visual review. This issue supplies their spec and baseline.

## Steps

1. Add the `design-proposal` skill: when to propose, the lifecycle, create,
   iterate, adopt, build against the spec, retire, and how to ask the owner.
2. Add `tools/check-proposals.ts` to `validate`, with `--stale` for gardening.
3. Route new visible features and material UI changes to the skill from
   deliver and research-and-design.
4. Add the stale-proposal step to weekly gardening.

## Acceptance criteria

- An agent that starts a new screen finds the skill from deliver.
- `check-proposals` fails a bad status, a wrong number of directions, a missing
  prototype for a live proposal, and a prototype left after the build shipped.
- `check-proposals --stale` lists a proposal with no choice after 14 days and
  an adoption whose issue is done.
