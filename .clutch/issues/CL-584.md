# CL-584: Log each wake that the timed read of the log finds lost

## Goal

A wake that a server process loses shows in the logs each time it happens, so the timed read of the log hides no loss.

## Context

CL-918 (PR #320) made live deltas cross server processes. A commit sends a wake inside its transaction. Each process has one reader per organization, which reads new events from the log on a wake, after the listener says `listening` again, and every 30 seconds (`rereadInterval` in `packages/sync/service/event-log.ts`).

The agent review of #320 raised a blocking finding under the rule "Fix the root bottleneck" (review comment 4646194132). The timed read is a net for a lost wake. When it finds events, nothing says that a wake was lost, so the net hides the loss. The PR also linked no issue for the root fix.

## Steps

1. Branch `clutch/cl-584-log-lost-wakes`.
2. Write the test first: a process whose wake hears nothing gets the events from the timed read and logs a warning. A process whose wake works logs no such warning.
3. When a read that the timer started finds events that no wake announced, log one warning. It names the organization, how many events the read delivered, and the sync IDs that it covered.
4. Name CL-920, the root proof of the wake, next to `rereadInterval` in the code and in `docs/contributing/architecture/server.md`.

## Files

- `packages/sync/service/live.ts`, `packages/sync/service/event-log.ts`, `packages/sync/service/live.test.ts`
- `docs/contributing/architecture/server.md`

## Acceptance criteria

- A timed read that finds events with no wake logs one warning with the organization, the count and the sync IDs.
- A process whose wake works logs no such warning.
- The comment of `rereadInterval` and `server.md` name CL-920.
