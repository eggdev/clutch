# CL-426: Run a scorer on Qwen on the Spark and record its score

## Goal

A scorer file in the factory tree runs on a Qwen model on the DGX Spark, judges one PR, and records its score where `clutch metrics` and C-Suite can read it. Layer 03 "Done when": a scorer runs on Qwen on the Spark and writes a score.

## Context

- Layer 03 of the factory stack. Read the Design section of CL-514 for the `scorer.md` and runner keys.
- The Spark serves Qwen with the OpenAI API:
  - Ollama: `qwen3.6:latest` at `http://localhost:11434/v1`.
  - llama-swap: `qwen3.8-27b` at `http://127.0.0.1:8092/v1`, with a 32,768-token context. llama-swap loads a model on the first call, so that call is slow.
- Both answered `GET /v1/models` on 2026-11-04. This costs no money.
- Warp's scorers: 1 to 20 labels with a score from 0 to 1, a pass mark, and a sample rate that is 25% by default.
- C-Suite's layer 04 row has a `task-compliance` scorer that judges each lane's PR against its work item. Clutch ships that scorer in the project tree, so C-Suite's scorer sweep can run `clutch score` in each project.

## Design (coordinator defaults, 2026-11-04)

- The runner file holds the model servers of its machine: a `models` map in `runners/<name>.yaml`, from a model name to its OpenAI base URL. Addition versus stack.md. Add the key to the CL-514 schema in this PR.
- `clutch score <scorer> --pr <number> [--repo OWNER/NAME] [--json] [--post]` reads the PR title, body, diff and its `.clutch/issues` file, sends the judge prompt and the labels to the scorer's model, and asks for JSON: `{ label, reason }`. The score is the label's score, and it passes when the score is at or above `pass_mark`.
- Cut the diff to fit the model's context, and say in the prompt that it was cut.
- Record each score in two places: print it, and with `--post` add a PR comment with a marker such as `<!-- clutch-score:<scorer>:<label>:<score>:<head sha> -->`, the same way as the dry-run verdicts. A project commits no score file, so no PR conflicts on it.
- `--sample` applies `sample_rate` for a sweep. Without it, the command always scores.
- Write no Qwen-only code path. Any `harness: qwen` model goes through the same OpenAI client. A `claude` or `codex` scorer may come later. Leave it out unless it is small.

## Steps

1. Branch `clutch/cl-426-qwen-scorer`.
2. Add the `models` runner key, and `qwen3.6` and `qwen3.8-27b` to `factory/runners/spark.yaml`.
3. Add `factory/scorers/task-compliance/scorer.md` with labels such as `complete`, `partial`, `off-task` and `broken`, `agents: [implement]`, `harness: qwen`, `model: qwen3.8-27b`, `runner: spark`.
4. Add `clutch score`, with tests that use a fake OpenAI server.
5. Run it on 3 merged Clutch PRs with each Qwen model. Put the scores, the time per call and your view of which model is good enough in the PR body.
6. Post one real score on one merged Clutch PR with `--post`.
7. Document the command in `apps/cli/README.md` and in the schema page.

## Acceptance criteria

- `clutch score task-compliance --pr <n>` on the Spark returns a label, a score and a reason from Qwen.
- One merged Clutch PR has a score comment with the marker.
- `clutch factory --check` fails on a scorer whose model is not in its runner's `models`, when its harness is `qwen`.
- `mise exec -- bun run validate` passes.
