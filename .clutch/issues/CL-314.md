# CL-314: Give each project triage, spec, implement, review and verify agents

## Goal

Each project's tree has 5 stage agents, built from Clutch's `deliver`, `run-lanes` and `verify` skills. Each stage hands off to the next through the PR and its tracker issue, so one lane run can take an issue through all 5. Layer 05 "Done when": a Neighborhood issue passes through all 5 stages in one lane run (CL-610).

## Context

- Layer 05 of the factory stack. CL-515 adds short agent files. CL-313 makes `verify` work.
- C-Suite's foreman picks the project and the agent, and launches the lane. Clutch owns the stages inside the project.
- `apps/cli/src/run-stage.ts` and `apps/cli/src/providers.ts` already run kickoff stages unattended with Claude or Codex. Reuse them.
- CL-913 (`later`) plans a delivery loop that takes an issue from `next` to merged. This issue builds the stage contract that loop needs. Leave CL-913 in `later` and link this issue in its notes.

## Design (coordinator defaults, 2026-11-04)

The schema follows C-Suite's `docs/stack.md` on main. Agent keys stay `role`, `description`, `harness`, `model` and `runner`. This issue adds no key. CL-516 adds `reads` later.

The hand-off contract. Each stage reads only the issue, the PR and the repository:

| Stage       | Reads               | Writes                                                         | Done when                                                   |
| ----------- | ------------------- | -------------------------------------------------------------- | ----------------------------------------------------------- |
| `triage`    | the issue           | phase, `depends_on`, `owner`, `status`, and a `## Triage` note | the issue is `in_progress`, or `blocked` with a reason      |
| `spec`      | the issue, the code | Steps, Files, Acceptance criteria and Verify                   | each criterion has a Verify command                         |
| `implement` | the issue, the PR   | the branch and the PR, with `bun run pr open`                  | validate is green                                           |
| `review`    | the PR, the issue   | one review comment with findings and a verdict                 | 0 blocking findings, or the findings go back to `implement` |
| `verify`    | the PR, the issue   | the screenshot comment (CL-313) and a proof note               | each criterion has proof                                    |

- `clutch agent prompt <name> [--issue CL-NNN] [--pr <n>]` prints the full prompt: the agent body, then the issue or the PR. `clutch agent run <name> ...` runs it with the agent's harness and model (`claude -p --model <id>` or `codex exec -m <id>`). A `qwen` agent fails with a clear "not supported yet" message. No stage agent uses Qwen now.
- A lane run is the 5 stages in order in one worktree. `review` sends work back to `implement` at most twice. Then the lane stops and asks. The contract page and the `review` and `implement` prompts say so.
- `clutch agent mark <stage>` adds a PR comment that starts with `<!-- clutch-stage:<role>:<head sha> -->`, through `apps/cli/src/pr-comment.ts` (CL-313), so the foreman and metrics can see which stages ran. `triage` and `spec` run before the PR exists, so their mark saves the marker in the Git common folder, and the first mark of `implement` posts it.

## Steps

1. Branch `clutch/cl-314-stage-agents`.
2. Write the 5 prompts in `factory/agents/`. Each names its skill, its inputs, its outputs and its stop rule.
3. Add `clutch agent prompt`, `clutch agent run` and `clutch agent mark`, with tests.
4. Write the contract on a docs page, and link it from the `deliver` and `run-lanes` skills.
5. Run one small Clutch issue through all 5 stages in one lane run, and link the PR.
