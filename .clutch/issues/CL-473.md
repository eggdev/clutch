# CL-473: Check a built screen against its adopted design before the merge

## Goal

A pull request that changes a screen shows that the build matches the design that the owner adopted. A build that matches merges with no person.

## Context

- The owner described the flow on 2026-11-12. He chooses the direction in the prototype and the design phase. Agents build to that design, review the build against it, and send screenshots. A layout change that matches an adopted design ships with no word from him.
- The `design-proposal` skill records the adopted direction, and the PR template names it. Nothing compares the build with it.
- The journeys take a screenshot of each screen on each web size, and `tools/journeys/visual-review.ts` posts them on the PR. A baseline shows a change. It does not say whether the change is the design.
- CL-446 is a council product review of a feature before it merges.

## Steps

1. Branch `clutch/cl-473-design-check`.
2. Read what the `design-proposal` skill stores for an adopted direction, and write down what a machine can compare: the screens, their states, and the image or the spec of each one.
3. Propose the check in a design proposal of its own, and let the owner pick: this is a design decision.
4. Build the pick: a check on the head of a PR that pairs each journey screenshot with its adopted design, and passes or lists the differences.
5. Post the screenshots and the verdict on the PR. A difference is a blocking finding. A new screen with no adopted design is a blocking finding too.

## Acceptance criteria

- A layout change that matches its adopted design merges with no person, and its PR shows the screenshots next to the design.
- A build that differs from its adopted design is held, with each difference named.

## Verify

- `mise exec -- bun run validate`
- One real PR with a matching change, and one with a difference.
