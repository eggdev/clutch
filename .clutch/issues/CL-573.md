# CL-573: Turn a value that projects fork into a clutch.yaml setting

## Goal

A project changes the first-screen module budget, or says that its own pipeline deploys, in `clutch.yaml`. It keeps no copy of a managed file for that.

## Context

- `tools/check-bundle.ts` holds the first-screen budget as a constant, `budget = 390` (line 19). Its message says to raise `budget` in that file. The file is managed, so a project that does so keeps a copy of the whole check.
- `deployProblem` in `tools/deploy.ts` (line 45) fails a project past kickoff that ships a web app and names no `deploy:` in `clutch.yaml`. `deploy:` takes only `command` and `url`, as `apps/cli/src/clutch-config/optional-keys.ts` reads it.
- A project that deploys from its own pipeline has no command to give. So it removes `check-deploy` from the checks, or keeps a copy of a managed file.
- Two projects kept a managed file only to change the first-screen budget, or to say that their own pipeline deploys.
- Neighborhood removed `check-deploy` from `nx.targets.checks.dependsOn` in `package.json`. Each sync put it back.
- `tools/guardrail-files.json` lists `clutch.yaml`. So agent review flags a change that raises a budget there, as it flags a change to the check itself.

### The rule

When a project keeps a managed file only to change a value, Clutch makes that value a setting in `clutch.yaml`. The default is Clutch's value, and the managed file reads the setting. This issue writes the rule and its first two cases.

## Steps

1. Branch `clutch/cl-573-settings-not-forks`.
2. Write the rule in the "Sync" section of `apps/cli/README.md`, next to the project differences of CL-568.
3. Add `budgets.first_screen_modules` to `clutch.yaml`, in `apps/cli/src/clutch-config/schema.ts`. It is a positive whole number.
4. Make `tools/check-bundle.ts` read it. Without the setting, the budget stays 390.
5. Add `bun tools/check-bundle.ts --adopt`. It writes the measured count of the largest first screen into `budgets.first_screen_modules`. A project runs it once, so the default is its count at adoption.
6. The budget only shrinks. When the count is below the setting, the check passes and prints the lower number to write. A change that raises the setting is a change to a guardrail file, which agent review flags.
7. Update the message of the check. It names `budgets.first_screen_modules` in `clutch.yaml`, not the constant.
8. Let `deploy:` take `pipeline` in place of `command`, in `apps/cli/src/clutch-config/optional-keys.ts`. `pipeline` names the workflow file of the project that deploys, such as `.github/workflows/release.yml`. `url` stays required, so the production proof still runs.
9. In `tools/deploy.ts`, `deployProblem` passes when `pipeline` names a file that exists, and fails when it does not. `runDeploy` prints one notice that names the pipeline, and deploys nothing.
10. Update the header comment of `.github/workflows/deploy.yml`, and the parts of `docs/contributing/setup/previews.md` and `docs/contributing/setup/checks.md` that describe `deploy:`.
11. Extend the tests:
    - `tools/check-bundle.test.ts`: the setting replaces the constant, a count over it fails, and `--adopt` writes the count.
    - `tools/deploy.test.ts`: `pipeline` with an existing file passes `check`, a missing file fails, and `run` deploys nothing.
    - `apps/cli/src/clutch-config/schema.test.ts`: both new keys, and a `deploy:` with both `command` and `pipeline` is an error.

## Acceptance criteria

- A project sets `budgets.first_screen_modules` in `clutch.yaml`, and `check-bundle` uses it with no edit to `tools/check-bundle.ts`.
- `--adopt` writes the measured count, and a later count above it fails.
- A project with `deploy: { pipeline, url }` passes `check-deploy` with `check-deploy` still in `nx.targets.checks.dependsOn`.
- `deploy:` with both `command` and `pipeline`, or with neither, is a config error.
- The "Sync" section of `apps/cli/README.md` states the rule: a value that projects fork becomes a setting.
- `mise exec -- bun run validate` passes.
