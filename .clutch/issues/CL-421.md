# CL-421: Fix the design-proposal skill where its first real run was clumsy

## Goal

The second design proposal costs less than the first. Each step of the
`design-proposal` skill names how to do it, and the check sees all of a
prototype.

## Context

The first real run: Neighborhood's change order approval screen, proposed in
eggdev/neighborhood#61, adopted in #63, built in #64. The friction is in
`.clutch/friction.jsonl` under CL-421. The largest items:

- The record names one `prototype` path. The real prototype spanned a gallery
  group, a board, a wide-page switch and a page in the `[group]` route.
- Nothing renders the adopted direction at `snap`'s geometry, or the real
  screen over the proposal's sample data. Both took throwaway pages.
- Gallery scaffolding counts toward `check-first-screen`, so a harness that
  stays in the app pushes the ratchet.
- Nothing tells an agent that the owner answered in the brief.

## Steps

1. Let `prototype` take a list of paths, and check each one.
2. Ship a proposal board and an adopted-page template with the skill, and say
   how to shoot the adopted direction at 390 px and 1280 px.
3. Add a Create step: check that each shown field exists in the screen's
   records.
4. Say how a project that is behind on Clutch runs the skill.
5. Decide how an owner's answer in the brief reaches an agent.
