# CL-586: Drop the records of a group whose load was cut off

## Goal

A record of a group that did not finish loading does not outlive that load. A record that the server deleted, or that moved to a group the person cannot see, never stays on the device because a load was cut off.

## Context

The review of 2026-11-20 found two cases, and confirmed both with probes.

- Case A: a first load at sync ID 0 gets one page of an eager group, with records r1 and r2. The writer tab saves them. The tab closes before the load ends. On the server, r1 is deleted. The next start pulls from 0, gets a snapshot with only r2 and then an empty delta at the head. `applyGroups` purges only records that are in no loaded group, so r1 stays for good.
- Case B: the socket drops between two pages of a lazy group load. The records of the pages that came stay in memory. The next load sends the snapshot as it is now, and a record that was deleted in between stays.

The pool hears of each page (`applyPage`) and of each loaded group (`applyGroups`), but not of the end of a pull. The engine listens for load requests (`onLoadRequest`) for the length of one pull, and stops listening when the pull ends.

## Steps

1. Branch `clutch/cl-586-cut-off-load` from `origin/main`.
2. Write the failing tests first: case A over the saves of `loadPool`, case B over the engine with handlers in memory, and a record of a loaded group that survives a cut-off load of another group.
3. When the engine stops listening for load requests, the pull has ended. Each group whose pages came and that did not load stops loading, and the pool drops each confirmed record that is in no loaded group.
4. A save never writes a confirmed record that is in no loaded group. It removes the row of such a record, and writes the record once its group loads.
5. The first `Groups` message of a pull from sync ID 0 ends the snapshot of every loaded group. The pool then drops each confirmed record that the pull did not send, so a copy that an older build saved in the middle of a first load recovers.
6. Update `local-first-sync.md`, `client.md` and `data-storage.md`.

## Acceptance criteria

- Case A: after the second start, r1 is not in the pool and not in the local database.
- Case B: after the second load of the group, the record that the server deleted is not in the pool.
- A record of a loaded group, and a record that is also in a loaded group, survive a cut-off load of another group.
- A save never writes a record that is in no loaded group.
- An older copy that holds part of a first load loses each record that the next pull from 0 does not send.
- `pool-conformance.test.ts` and `reference-pool.ts` pass unchanged.
- `transport.ts` and the protocol do not change.
