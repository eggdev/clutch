# CL-588: Make the cost of a pool change follow what changed

## Goal

One change to the object pool costs what it changed, not what the pool holds. A delta that touches 3 records, with 2 waiting transactions, copies and compares no other record.

## Context

`recompute` in `packages/sync/runtime/pool.ts` copied every confirmed table on each change, replayed every waiting transaction over the copy, and compared every record with the one before (`copy`, `draftOver` and `keepUnchanged` in `tables.ts`). The review of 2026-11-20 measured about 25 ms for one local edit with 100,000 records in memory, and each live delta paid the same.

## Steps

1. Branch `clutch/cl-588-change-cost`, stacked on CL-587.
2. Measure the cost of one local edit and of a delta of 3 records with 100,000 records and 2 waiting transactions, with a script kept outside the repository.
3. Write the failing test first: a pool option `compared` hears how many records each change put in step, and each saved record notes when the pool reads it.
4. The confirmed records name the keys that changed since the last change of the pool, or all of them after a load or a reset.
5. The waiting changes write over the confirmed records into a set of writes, and never into the confirmed records.
6. The visible tables compare only the changed keys and the keys that the waiting changes wrote, now and the time before.
7. Update `local-first-sync.md` and `client.md`.

## Files

- `packages/sync/runtime/pool.ts`, `tables.ts`, `confirmed.ts`, `pool-doors.ts`

## Acceptance criteria

- A delta of 3 records with 2 waiting transactions puts 5 records in step and reads no other record.
- A local edit and its rejection each put 3 records in step.
- `pool-conformance.test.ts` and `reference-pool.ts` pass unchanged.
- Unchanged records stay the same objects, and only the watchers of changed records and models wake.
- The PR states the measured cost before and after for 100,000 records.
