# CL-033: Close the verify runner ownership race and its flaky tests

## Goal

A runner killed right after it starts a flow never leaves an untracked flow, and `tools/verification/test_verify.py` passes on every run.

## Context

From the CL-029 review:

- `spawn_owned` (`tools/verification/processes.py:92-98`) starts the flow with `Popen`, runs `ps` for its birth time, and only then writes `command-owner.json`. A SIGKILL in that window leaves a flow that no record owns, and the next run goes ahead. This is the CI failure of `test_force_loss_is_reconciled_before_another_flow_and_never_replayed` (run 41058195263).
- `start_waiting_flow` (lines 163-166) returns as soon as `flow.pid` exists, and can read it while it is still empty.
- `test_timeout_stops_descendant_even_after_group_leader_exits` (line 199) has a 1 s timeout. `test_detached_output_writer_has_a_deadline_and_retains_uncertain_ownership` (line 267) has 0.5 s. Both can expire before the worker starts.
- Lines 47-48 assert that evidence "survives stop" when `stop` never touches it. The test at line 141 covers this properly.

## Steps

1. Product: write an intent record before `Popen`, or hold the child on a pipe until the record is saved.
2. `start_waiting_flow`: poll until `flow.pid` parses and `command-owner.json` records the same pid.
3. Raise the two timeouts to 3 s and 2 s. Fail with "worker never started" when `child.pid` is missing.
4. Drop lines 47-48 and `_and_stop` from that test name.

## Acceptance criteria

- The force-loss test passes 50 times in a row locally.
- validate passes.
