# CL-569: Carry a project's edit to a managed file with a three-way merge

## Goal

A project that edited a managed file keeps its edit through each sync. Sync merges Clutch's new copy into the edit, and asks only when the two really conflict.

## Context

- `planDesired` in `apps/cli/src/sync/engine.ts` (line 101) makes a conflict of each managed file whose hash matches neither the lineage nor a `known` hash. It does so even when Clutch did not change the file.
- `settle` in `apps/cli/src/sync/run.ts` (line 57) takes or keeps the whole file. A kept file goes into `kept` of `.clutch/lineage.json`, with the hash of Clutch's copy that the project declined. Sync asks again on each sync that changes Clutch's copy.
- Sync stores only hashes. It never merges three ways.
- `pin.ts` is the one place that takes Clutch's copy silently when the project did not edit the file since the last sync.
- Neighborhood's sync to v1.13.1 needed 14 three-way merges by hand. Most kept one line, such as one `nosemgrep` line in `.github/workflows/deploy.yml`, or a budget in `tools/check-bundle.ts`.

### Terms

- The **base** of a managed file is Clutch's copy at the last sync. The project's copy is the base plus the project's edit.
- A **carried edit** is a project edit that sync keeps by a clean three-way merge of the base, the project's copy and Clutch's new copy.

### Where the base comes from

The base is already known, as a hash. `nextLineage` in `apps/cli/src/sync/lineage.ts` writes the hash of each of Clutch's managed files into `files`, for a kept file too. So `files[path]` is the hash of the base.

The hash alone cannot find the content. `fingerprint` in `apps/cli/src/review-source.ts` hashes the mode and the bytes with SHA-256. It is not a git blob id.

So sync reads the base from the Clutch checkout that it already uses: `git show <templateCommit>:<path>`. `loadClutchSource` in `apps/cli/src/sync/source.ts` reads each file in this way. A shallow checkout may lack that commit. `releaseCommit` in `apps/cli/src/sync/seed-changes.ts` already fetches a missing tag, and the base read does the same. Sync uses the base only when its fingerprint equals `files[path]`.

One case breaks this. A sync with `--only` moves `templateCommit`, but keeps the old record of each file outside its scope (line 68 of `lineage.ts`). For such a file, `nextLineage` records the old commit in a new map, `bases`, by path. Sync reads `bases[path]` first, then `templateCommit`.

Store a commit, not the base content. Content would make the lineage as large as the managed files, and each sync PR would show it.

A file that the project kept before this change needs no migration. Its `kept` hash equals `files[path]`, so the copy at `templateCommit` is its base. In that case the owner saw that copy and chose the project's copy, so it is the right base.

## Steps

1. Branch `clutch/cl-569-carried-edits`.
2. Read `templateCommit` in `readLineage`, and add `bases` to the lineage type in `apps/cli/src/sync/lineage.ts`. `nextLineage` writes `bases` for the files that a scoped sync leaves.
3. Add a function that reads the base of one path, as "Where the base comes from" says. It returns nothing when the commit cannot be fetched or the hash differs.
4. In `apps/cli/src/sync/run.ts`, after `plan`, handle each conflict whose base can be read and whose three copies are text files:
   - Clutch's copy equals the base: Clutch did not change the file. Leave the project's copy, and write nothing.
   - Both changed: merge with `git merge-file -p` on the three copies. A clean merge writes the result and adds the file to a new `carried` list.
   - A real conflict stays a decision, as today.
5. Ask once per file. When the file has no `kind: edit` entry in `differences:` of `clutch.yaml`, it is a decision, even when the merge is clean. The owner records the reason with `--keep <file> --reason "<text>"`, which writes that entry. After that, sync does not ask again about the file, unless a later merge has a real conflict.
6. Add `--merge <file>` for a real conflict. Sync writes the file with conflict markers, labeled `project`, `base` and `clutch <release>`. It records Clutch's new copy as the base, and exits 2. `clutch sync --check` fails while a managed file holds conflict markers.
7. Report the result. The text output and `--json` get `carried`, with each file and the count of project lines that differ from Clutch's copy. `.github/workflows/clutch-sync.yml` lists the carried files in the PR body.
8. Write `carried` into the lineage of the sync. In `tools/github/bot-rule.ts`, `syncProblems` (line 159) gives one problem for each carried file. So a sync PR that carries an edit is not a pure sync, and goes through agent review and the merge judge.
9. When a carried file matches `tools/guardrail-files.json`, the problem says that the owner approves the head, as `gardeningProblems` does. Workflows, checks and the merge gate match those patterns.
10. Extend the tests:
    - `apps/cli/src/sync/decide.test.ts`: a clean merge carries the edit. A real conflict asks. `--merge` writes markers. An unchanged Clutch copy asks nothing once the difference is recorded.
    - `apps/cli/src/sync/run.test.ts`: the base read through `templateCommit` and through `bases` after `--only`. A base that cannot be read falls back to a decision. A file kept before this change merges with no migration.
    - `tools/github/bot-rule.test.ts`: a carried file fails the sync rule, and a carried guardrail file needs the owner.
11. Update the "Sync" section of `apps/cli/README.md` and the comment at the top of `clutch.files.yaml`.

## Acceptance criteria

- A project edit to one line of a managed file survives a sync where Clutch changed another part of the file. Sync asks nothing once the file has a `differences:` entry.
- Clutch did not change a managed file that the project edited. Once the difference is recorded, sync asks nothing and writes nothing to the file.
- An edit that conflicts with Clutch's change is a decision. `--merge` writes conflict markers, and `--check` fails until they are gone.
- A sync that cannot read the base acts as sync acts today.
- The text output, `--json` and the sync PR body list each carried file.
- A sync PR that carries an edit fails the sync bot rule. One that carries an edit to a guardrail file also needs the owner's approval.
- A file kept before this change merges on the next sync with no extra step.
- `mise exec -- bun run validate` passes.
