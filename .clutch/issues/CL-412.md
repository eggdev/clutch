# CL-412: Compare journey screenshots with committed baselines

## Goal

CI fails when a screen's pixels change and no baseline was updated. Each screen is captured at a mobile and a desktop width, in light and dark. The baselines are committed PNG files.

## Context

Nothing in build or review looks at pixels. None of Neighborhood's last 15 merged PRs has an image, and PR #51 says "Not verified: the gallery in a browser". Agent review reads only the diff. In the 75-repo study (`software-factory/design/README.md`), the strong setups are self-built: VS Code fails CI on a screenshot-hash mismatch, and PostHog runs Visual Review in its merge queue. Hosted visual-diff services are rare: Chromatic 2, Argos 1, Percy 1.

## Design note (CL-412, CL-413, CL-414)

### Flow

1. **Capture.** A journey calls `snap(page, 'name')` from `@repo/journeys/testing/visual` at a stable point, the same way it calls `accessible(page, 'where')`. `snap` captures the page 4 times, at 390 px and 1280 px wide and in the light and dark schemes. It changes the viewport and the `dark` class on `<html>` in place, so the journey does not run 4 times. A gallery or component page is a journey that opens each group and snaps it.
2. **Determinism.** Animations off (`animations: 'disabled'` and reduced motion), the caret hidden, `document.fonts.ready` awaited, the `en-US` locale and the UTC time zone. `snap` takes shots until two in a row match, at most 5, as `toHaveScreenshot` does. A dynamic region, such as a generated title, is passed as `mask`. A screen that shows the time sets a fixed clock (`page.clock.setFixedTime`) itself, since a global fixed clock would change the journey's own timestamps.
3. **CI is the only renderer.** Fonts and anti-aliasing differ between machines (this one is arm64 and CI is x86-64 Ubuntu), so a baseline comes from CI. Locally, `snap` writes the PNGs to `test-results/visual/` for the agent to look at, and asserts nothing, so the pre-push journeys stay green. In CI (`CI=1`) it compares each shot with the baseline at `<journey folder>/__screenshots__/<name>-<mobile|desktop>-<light|dark>.png`, with a 0.1% pixel tolerance. A missing or different baseline fails the required `journeys` check.
4. **Update.** In CI, `snap` writes only the changed and new shots to `test-results/visual/`, at their baseline paths, and the `journeys` job uploads that folder as the `visual-screenshots` artifact. `mise exec -- bun run visual pull <pr>` downloads that artifact from the PR's latest CI run and writes each changed or missing PNG into its baseline path. The agent commits the PNGs and states the reason in the PR body. That is the whole update loop: no CI push and no new token.
5. **Review (CL-413).** A step in the `agent-review` job, which is already required and already holds the Anthropic credential, lists the baseline PNGs that the PR adds, changes or removes. With none, it ends before any install or API call. Otherwise it sends each before/after pair, the PR title and body, `docs/principles/design-tokens.md` and the styling roles to `claude-haiku-5-5`, in batches of 8 pairs. It asks for one structured verdict per pair: `explained`, `broken` and a one-line note. It posts or edits one comment on the PR that shows before and after for each pair, with the verdict, using `https://github.com/<repo>/blob/<sha>/<path>?raw=true` image links at the base and head commits. It fails the step only for a pair that is unexplained or broken. So a PR that updates baselines with a clear reason still auto-merges.
6. **Owner view (CL-414).** The weekly digest adds a contact sheet for each fleet repository: each baseline that changed on the default branch in the last 7 days, before and after as 200 px thumbnails, linked to the merge that changed it. Brendan reads one page a week instead of approving each PR.

### Baseline format

A baseline is a plain PNG at `<folder>/__screenshots__/<name>-<width>-<scheme>.png`, where `<width>` is `mobile` (390 px) or `desktop` (1280 px) and `<scheme>` is `light` or `dark`. Lane F's adopted design proposals can seed a baseline by copying their PNG to that path. CI then confirms it or replaces it through `visual pull`.

### Cost per PR

- CI: `snap` adds about 1 s per name (4 shots, plus the stability retakes) to the `journeys` job. The template has 2 names; Neighborhood's gallery would have 10.
- GitHub API: `visual pull` makes 2 calls (find the run, download the artifact). The review step makes 0 calls when no baseline changed. Otherwise it makes 1 call to list comments, 1 to post or edit, and 1 for the PR body. The digest makes 0 calls: it reads `git log` in the checkout it already has.
- Model: Haiku 5.5 is $0.10 per million input tokens and $0.50 per million output tokens. An image costs about width × height / 750 tokens, and the API scales an image down to a 1568 px long edge. A desktop shot is about 1,230 tokens, and a mobile shot about 1,600 at most. A pair plus its share of the prompt is about 4,000 tokens, so 8 pairs come to about 32,000 input tokens and 1,000 output tokens: **about $0.004 a batch**. The measured figure goes in CL-413. A PR that changes no baseline costs $0.

### Flaky diffs

- The stability retakes and the tolerance absorb anti-aliasing noise.
- A screenshot that differs on the same code goes in the existing quarantine, `tools/flaky-tests.json`, with an issue and an expiry. `file` is the journey and `name` is the snap name. `snap` still captures and uploads a quarantined name, but logs a warning instead of failing. `check-flaky-tests` accepts a `.pw.ts` journey whose source has `snap(page, '<name>')`. A quarantine is a new escape hatch, so it ships with CL-413, the other change that needs the owner.
- A runner-image change that moves every screenshot at once is fixed by one baseline refresh PR made with `visual pull`. The review sees "every pair changed by a few pixels, with no UI code changed" as explained when the PR body says so.

## Steps

1. Add `packages/journeys/testing/visual.ts` with `snap`, and the deterministic settings in `tools/journeys/playwright.config.ts`.
2. Snap the home page and the notes screen in `features/notes/journeys/notes-sync.pw.ts`.
3. Upload `test-results/visual` from the `journeys` job, and add `tools/journeys/visual-pull.ts` and the `visual` script.
4. Generate the first baselines in CI, and commit them with `visual pull`.
5. Document it in `docs/contributing/setup/verification.md`.

## Acceptance criteria

- In CI, a changed pixel on the home page fails `journeys` and uploads the new screenshot.
- `visual pull <pr>` writes the CI screenshots into the baselines.
- Locally, journeys pass and write the screenshots to `test-results/visual/`.
