# CL-443: Prove the core journeys on production after each deploy

## Goal

The core journeys run on production after each deploy. A red run starts a revert and opens a T3 thread for the owner. A green run contacts no one.

## Context

- `docs/principles/proof-gates-code.md`: a skipped deploy is red, and the core journeys run on production after each deploy.
- On Neighborhood, eggdev/neighborhood#36 skipped the web deploy "until production is configured", and the skip showed green. Production served an old build for about a week. Agents checked `/api/health` and said sign-in worked, and no one had signed in.
- `tools/github/main-watch.ts` (CL-436) watches CI on `main` after a merge, and `auto-revert.yml` reverts a red `main`.

## Steps

1. Add a production run mode to `tools/journeys/run.ts`: the core journeys against the deployed URL. Each run signs up a new account on an address of the project's test inbox, named in project intent (a catch-all domain or a mail API such as Mailosaur), and deletes the account after. A failed delete files a friction entry with the account.
2. Prove checkout on production in live mode with a $0 plan or a full-discount code, and cancel the subscription after. Never charge a real card.
3. Make the template's deploy step fail, not skip, when production is not set up, once kickoff names a host.
4. Record each deploy's commit on the default branch with its result, in the deploy job's summary and a `deploy/<env>` commit status. The PRs of a deploy are the merge commits on the first-parent history between the previous deploy's commit and this one. The revert chain reverts only those.
5. After the deploy, run the production journeys. On red, run the failed journey again once. When it fails again and passed on the previous deploy, start a revert chain: revert the PRs merged since that deploy one at a time, newest first, and run the journey after each revert. Stop when it passes. Revert at most 3 PRs. When the journey still fails, or it also fails on the previous deploy, revert nothing more and open a T3 thread for the owner with the runs.
6. One controller run owns a revert chain from start to end. It marks each revert deploy it makes. The post-deploy run skips a deploy with that mark, and any deploy while a `deploy-hold` issue is open, so no second chain starts. No merge lands while the chain runs. These steps finish, in order, before the first revert:
   - It opens one issue labelled `deploy-hold` that names the chain's run. The hold belongs to no commit, so a revert does not drop it.
   - `pr merge`, the Auto-merge judge and the merge job's `--enable` step each refuse while such an issue is open, and each labels the PR it refuses `deploy-held`. The decide and merge jobs get `issues: read`, and the bot token gets `permission-issues: read`, so they can read the hold.
   - It waits for the Auto-merge runs in progress to finish, then cancels each queued GitHub auto-merge with `gh pr merge --disable-auto`, and labels those PRs `deploy-held` too.

   When the chain ends, green or not, it closes the issue, waits again for the Auto-merge runs in progress, and only then lists the `deploy-held` PRs. It removes each label and dispatches Auto-merge for that PR, so no PR stays stranded.

7. Give `pr merge` one more wait: the production journeys on the merge's deploy.
8. When a production journey fails, open a T3 thread for the owner with the journey, the failure, the revert and a link (CL-445). A green run contacts no one.

## Acceptance criteria

- A deploy that is not set up fails its job.
- A production sign-in journey that fails twice after a deploy reverts the newest PR first, and stops at the revert that makes it pass.
- A journey that also failed on the previous deploy reverts nothing, and opens a T3 thread.
- A revert chain touches only the PRs merged between the previous deploy's commit and the failed one.
- While a revert chain runs, `pr merge` and the Auto-merge judge refuse every merge.
- A PR whose auto-merge was queued before the chain, or armed by a merge job that started before it, does not merge during it.
- Each PR that the hold refused or cancelled, in `pr merge`, the judge or `--enable`, is judged again when the chain ends.
- A deploy while the hold is open starts no second chain.
- The hold stays through every revert of the chain, and the chain closes it when it ends.
- `pr merge` exits 1 when the production journeys fail.
- `bun run validate` passes.

## Verify

`mise exec -- bun run validate`, and a production run against a preview deploy with a broken sign-in.
