# CL-443: Prove the core journeys on production after each deploy

## Goal

The core journeys run on production after each deploy. A red run starts a revert and opens a T3 thread for the owner. A green run contacts no one.

## Context

- `docs/principles/proof-gates-code.md`: a skipped deploy is red, and the core journeys run on production after each deploy.
- On Neighborhood, eggdev/neighborhood#36 skipped the web deploy "until production is configured", and the skip showed green. Production served an old build for about a week. Agents checked `/api/health` and said sign-in worked, and no one had signed in.
- `tools/github/main-watch.ts` (CL-436) watches CI on `main` after a merge, and `auto-revert.yml` reverts a red `main`.

## Steps

1. Add a production run mode to `tools/journeys/run.ts`: the core journeys against the deployed URL. Each run signs up a new account on an address of the project's test inbox, named in project intent (a catch-all domain or a mail API such as Mailosaur), and deletes the account after. A failed delete files a friction entry with the account.
2. Prove checkout on production in live mode with a $0 plan or a full-discount code, and cancel the subscription after. Never charge a real card.
3. Make the template's deploy step fail, not skip, when production is not set up, once kickoff names a host.
4. After the deploy, run the production journeys. One controller run owns a revert chain from start to end. It marks each revert deploy it makes, and the post-deploy run skips a deploy with that mark, so a revert never starts a second chain. On red, run the failed journey again once. When it fails again and passed on the previous deploy, revert the PRs merged since that deploy one at a time, newest first, and run the journey after each revert. Stop when it passes. Revert at most 3 PRs. When the journey still fails, or it also fails on the previous deploy, revert nothing more and open a T3 thread for the owner with the runs.
5. Give `pr merge` one more wait: the production journeys on the merge's deploy.
6. When a production journey fails, open a T3 thread for the owner with the journey, the failure, the revert and a link (CL-445). A green run contacts no one.

## Files

- `tools/journeys/run.ts` and its test
- `tools/github/main-watch.ts`, `tools/github/merge.ts`
- the deploy workflow in the template
- `docs/contributing/operations/rollback.md`

## Acceptance criteria

- A deploy that is not set up fails its job.
- A production sign-in journey that fails twice after a deploy reverts the newest PR first, and stops at the revert that makes it pass.
- A journey that also failed on the previous deploy reverts nothing, and opens a T3 thread.
- `pr merge` exits 1 when the production journeys fail.
- `bun run validate` passes.

## Verify

`mise exec -- bun run validate`, and a production run against a preview deploy with a broken sign-in.
