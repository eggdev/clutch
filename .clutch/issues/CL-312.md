# CL-312: State the setup and check commands in a runner file

## Goal

Each project states its setup command and its check command once, and one command makes a fresh worktree that is ready and checked. Layer 02 "Done when", first half: a Neighborhood lane passes its check in a new worktree (CL-609).

## Context

- Layer 02 of the factory stack. Read the Design section of CL-514 for the runner keys. CL-515 adds `factory/runners/spark.yaml`.
- `clutch worktree new` already copies `worktree.copy` and runs `worktree.setup` from `clutch.yaml` (`apps/cli/README.md#worktree`). No key states the check command.
- C-Suite's foreman launches a lane from the runner file, with no ids typed in chat. So the runner file must name all a launch needs: the machine, the T3 environment, the workspace and the commands.

## Design (coordinator defaults, 2026-11-04)

- The runner keys follow C-Suite's `docs/stack.md` on `main`: `description`, `machine`, `t3_environment`, `workspace` (`worktree` or `main_checkout`), and the optional `ssh` and `setup`.
- Keep one source for each command. `clutch.yaml` keeps `worktree.setup`, and gets `worktree.check`, which defaults to `mise exec -- bun run validate`. The runner's `setup` holds only what the machine needs before the project setup. Write this split in the schema page.
- Add no runner `check` key until a real machine needs a different check. The Spark does not.
- `clutch worktree new <slug> --runner <name> --check [--json]` runs the runner's `setup`, then `worktree.setup`, then `worktree.check`. It exits with the check's result, and keeps the worktree when the check fails.
- `--json` prints one line with the path, the branch, the runner and the check result, so the foreman can read it.
- The setup, the check and the runner come from the new checkout, so they match its code. The main checkout on the Spark can be far behind `origin/main`.

## Steps

1. Branch `clutch/cl-312-runner-commands`.
2. Add `worktree.check` to the `clutch.yaml` schema and to its docs.
3. Add `--check`, `--runner` and `--json` to `clutch worktree new`, with tests.
4. Make the runner keys match stack.md in the CL-514 schema and the schema page. Remove the setup from `factory/runners/spark.yaml`, because it repeats `worktree.setup`.
5. Make a worktree of Clutch with `--runner spark --check`, and put the time and the result in the PR body.

## Acceptance criteria

- `clutch worktree new smoke --runner spark --check` makes a worktree, sets it up, runs the check and exits 0 in Clutch.
- A failing check exits non-zero and keeps the worktree, so a person can look.
- `mise exec -- bun run validate` passes.

## Verify

```bash
mise exec -- bun run clutch worktree new smoke --runner spark --check --json
mise exec -- bun run clutch worktree rm smoke --force
```
