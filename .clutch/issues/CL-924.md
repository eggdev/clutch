# CL-924: Compile journeys to agent-device commands and drop the Maestro flow format

## Goal

A journey in data form runs on a device through `agent-device` commands only. The repository holds no Maestro flow.

## Context

The owner asked on 2026-11-21 what dropping the Maestro format would need. That decision is the owner's. This issue holds the facts, and no agent starts it before the owner decides.

CL-594 already runs part of each journey outside Maestro. A check of a text field value, a fill of such a field, each script and each screenshot are native `agent-device` commands or runner code. The Maestro flow still carries the launch, each tap, each text entry and each wait for a text.

What a change must replace:

- The compile target. `tools/journeys/maestro.ts` writes a Maestro flow. Each step has a native command: `open --relaunch --launch-args` for a launch, `press` for a tap, `fill` for a text entry, `wait` and `wait absent` for a check, `screenshot` for a shot. The clear of the app state at the first launch needs a native form.
- The cut into parts. `tools/journeys/flow-parts.ts` and the script host exist only because a remote flow takes no script. With one command for each step, the runner calls the tool and the server check in TypeScript.
- Each native journey that a person writes as `features/<feature>/journeys/<id>.maestro.yaml`, and the core journey rules that read that form: `tools/check-journeys.ts`, `tools/journeys/core-rules.ts`, `tools/github/weaker-journeys.ts` (it counts `label: outcome` lines) and `apps/cli/src/doctor/core-journeys.ts`.
- The docs and the skills that name the format.

A cost: one command for each step is slower than one flow for a stretch of steps. Each `agent-device` call took about 1 second in the trial.

## Steps

1. The owner decides whether the format goes.
2. Write the plan from the list above.
