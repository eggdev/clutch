# CL-466: Guard shell writes to guardrail files, and keep the guard on in the template

## Goal

An agent that changes a guardrail file through the shell hears it at once. The guard also runs in the template repository.

## Context

- `.claude/settings.json` and `.codex/hooks.json` send `Edit` and `Write` to `guard-guardrails`. A shell command, such as `sed -i`, changes the same file with no question.
- `tools/agent-hooks/guard-guardrails.ts` lets each edit through while `KICKOFF.md` exists. The template keeps `KICKOFF.md` for good, so the guard never runs in the template.
- No merge rule holds a guardrail change: it merges on proof, see decision record 0005. The merge judge holds only a weaker journey or budget. This issue is session advice: the agent hears of the change while it can still undo it.

## Steps

1. Branch `clutch/cl-466-guard-shell-writes`.
2. Write the failing tests first, in `tools/agent-hooks/agent-hooks.test.ts`.
3. After a shell command, compare the guardrail files of the working tree with their state before the command. When one changed, tell the agent which file, and that a person approves each change.
4. Find how the CLI tells the template from a project, and use it: the guard is off only during the kickoff of a project.
5. Move `docs/contributing/harness-engineering.md#agent-hooks` with the behavior.

## Files

- `tools/agent-hooks/`, `.agents/hooks/`, `.claude/settings.json`, `.codex/hooks.json`

## Acceptance criteria

- A shell command that changes `oxlint.config.ts` ends with a message that names the file and the rule.
- In the template repository, an `Edit` of a guardrail file asks the person.
- A project in kickoff still edits these files with no question.
