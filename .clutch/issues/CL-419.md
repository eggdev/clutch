# CL-419: Hold for the owner only the hard core and a weaker merge check

## Goal

Brendan approves only the hard core. A PR waits for him when it changes a hard-core path, or when it weakens a check that gates the merge. Nothing else routes to him. Brendan, 2026-11-04: "Narrow your required review to the real hard-core files, and keep the wipe-on-push for those."

## Context

Lane G measured every Brendan approval and dismissal in the last 60 merged Clutch PRs (#118 to #191) and the last 54 merged Neighborhood PRs (#1 to #62). It used 3 GraphQL queries per repository. The scripts read each PR's files, reviews, dismissal events, force pushes and commits. They also read each inline agent review comment whose first line starts with `owner`, the same match that `agent-review.yml` uses. They matched the files against the CODEOWNERS file of the PR's base commit.

### Why he was asked to approve

1. **Most approvals were real hard core.** The merge gate was being built (#148 to #179), decision records came in (#183, nbhd#60), and Neighborhood synced Clutch's gate files (nbhd#34, #37, #53). That work fades as the gate settles.
2. **Before #148 (2026-11-02), CODEOWNERS held most of the repository.** It covered skills, workflows, `clutch.yaml`, `package.json`, the doctor baseline and lint config. That accounts for 12 of the 17 approvals from #118 to #146. #148 already narrowed it to the hard core.
3. **The owner finding fired on more than the hard core.** 9 Clutch PRs and 3 Neighborhood PRs touched no CODEOWNERS path and went to him only for an `owner` finding. Most of those findings are real weakenings: a knip entry, a raised budget (nbhd#47, 150 kB to 620 kB), a skipped check (#171), a lint ratchet hatch (#181). Five were not: #153 and #154 (a skill's intake script), #170 and #173 (`pr merge` and `pr status`, helpers that do not gate the merge) and #185 (the tolerance of a new screenshot compare). The rule said "a check" with no limit, so the agent counted any helper or new option.
4. **`docs/contributing/review.md` mixed the gate with a description of the job.** It holds the rules agent review applies (the gate) and also how the job runs, visual review and the labels table (a description). The "docs did not move with behavior" rule then sent every change to the job's behavior to that owner-only page (#159, #166, #168, #176, #186). Only #168 had no other hard-core path.

### Why he was asked again

The 19 extra approvals came from pushes after his approval. The ruleset's `dismiss_stale_reviews_on_push` dismissed each one:

- Fixes for review findings that arrived after the approval: #148, #152, #186 (5 dismissals), nbhd#52, #57, #60.
- A rebase that carried new commits along with it: #143, #149, #163, #186.
- A tracker commit after approval (`mark CL-NNN done`): #134, #138, #189. Since then `pr open` marks the issue `done` before the first push, and the release job writes `TRACKER.md`.

### Does a sync keep an approval?

Lane G ran a test in `eggdev/clutch-ruleset-probe`, a public scratch repository. It has the same `pull_request` rule (`dismiss_stale_reviews_on_push: true`). The `github-actions` bot approved four PRs, then `main` moved under them:

| Push after the approval                                                   | Approval                      |
| ------------------------------------------------------------------------- | ----------------------------- |
| GitHub's "update branch" (`PUT /pulls/<n>/update-branch`, a merge commit) | kept, also on a second update |
| A local `git merge origin/main`, pushed                                   | kept                          |
| `git rebase origin/main`, force-pushed                                    | kept                          |
| A new commit that changes the PR's diff                                   | dismissed                     |

GitHub dismisses an approval only when the PR's own diff changes. A clean sync with `main` keeps it, whichever way it is made. Every Clutch dismissal came from a push that changed the diff. So the order of work is the fix: finish every fix before asking him, and after the approval push only a sync or a blocking fix. CL-420 makes the babysitter do that. It syncs by merge, as kibana's `pr-babysit` does, because a merge needs no force push. A conflict that a sync resolves changes the diff, so expect it to dismiss the approval. The test did not cover that case.
