# CL-921: Tell each sync client when the server can take its pull again

## Goal

A sync client pulls again when the server says that it can take the pull, not after a wait that it guesses.

## Context

When a pull or a push fails, the transport waits and tries again (`retryWait` in `packages/sync/runtime/transport.ts`). The wait starts at 200 ms and grows to 3 seconds. CL-592 makes it start again from 200 ms after a pull that heard the server, and spreads it by a random part, so the clients of a server that comes back do not all pull at the same moment.

That wait is a guess. The client cannot know when a server that restarts, deploys or sheds load can take its pull. This issue is the root fix that the rule "Fix the root bottleneck" asks the wait to link: the server tells each client when to come back.

Trigger: the owner decides how the server announces that it stops and starts, such as a drain close code on deploy and a load signal.

## Steps

1. Branch `clutch/cl-921-pull-when-server-ready`.
2. Pick the signal with the owner: for example, a close code with a time to wait, sent when a process drains for a deploy.
3. Make the transport wait for that signal when the server sent one, and keep the spread wait only for a socket that dropped with no word.
4. Test it over the real socket with two API processes, one of which drains.

## Files

- `packages/sync/runtime/transport.ts`, `packages/sync/runtime/server.server.ts`, `packages/sync/runtime/socket-ends.server.ts`
- `apps/api/src/processes.test.ts`
- `docs/contributing/architecture/local-first-sync.md`

## Acceptance criteria

- A client whose server drains for a deploy pulls again when the server says, not after a guessed wait.
- A socket that drops with no word still tries again after the spread wait.
