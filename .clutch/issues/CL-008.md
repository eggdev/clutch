# CL-008: Add the capability registry format and detection engine

## Goal

A registry file lists every capability and how to detect it. A detection engine turns a repository into `present`, `partial`, `missing` or `unknown` for each capability.

## Context

- The glossary defines "Registry" as "A file that lists every instance of one thing. A check reads it." It says not to call it a manifest. Model it on `docs/contributing/architecture/primitives.yaml`.
- The registry lives at `docs/contributing/capabilities/registry.yaml`, next to the one-page-per-capability docs (CL-018).

## Registry entry format

```yaml
version: 1
capabilities:
  - id: codeql_sast # snake_case, matches the research dataset id
    name: CodeQL / SAST
    category: Trust # Agent context | Verification | Lint & guardrails | Trust | Parallel work | Review & merge | Scale loops
    phase: P1 # the Clutch phase that adopts it
    level: core # core: an unwaived gap fails doctor --check; extra: a warning only
    effort: S
    research: { rank: 16, priority: 44.6, adoption_top: 0.30 }
    doc: docs/contributing/capabilities/codeql-sast.md
    detect: # all rules pass = present; some pass = partial; none = missing
      - any:
          - workflow: { uses: github/codeql-action/ }
          - remote: code_scanning_default_setup
    partial_if: # optional extra rules; when only these pass = partial
      - file: .github/workflows/security.yml
```

## Rule kinds

- `file: <glob>`: at least one file tracked by git matches. `min: N` raises the count. `exclude` is a list of globs.
- `grep: { files: <glob>, pattern: <regex> }`: a tracked file matches the regex.
- `script: <name>`: the root `package.json` `scripts` has it.
- `target: <name>`: the root `package.json` `nx.targets` has it, or any `project.json` or package `nx.targets` has it.
- `workflow`: a file in `.github/workflows/*.yml` matches it. The fields are `{ on?: <event>, uses?: <prefix>, run?: <regex>, pinned?: true }`. `pinned: true` passes only when every `uses:` ref is a 40-hex SHA.
- `yaml: { file, path }`: the YAML or JSON path exists in the file.
- `remote: <probe>`: a named GitHub probe. It returns `unknown` without `--remote` (CL-020).
- `any: [rules]` and `all: [rules]` nest.

## Status rules

- `present`: every top-level `detect` rule passes.
- `partial`: some top-level rules pass, or only `partial_if` rules pass.
- `missing`: no rule passes.
- `unknown`: every top-level rule is `unknown`.
- An `unknown` rule counts as not passed. Inside `any`, an `unknown` child is ignored unless every child is `unknown`.

## Steps

1. Branch `clutch/cl-008-registry-engine`.
2. Add `apps/cli/src/doctor/registry.ts`, which parses and validates the registry: unique ids, a known category, phase and level, `doc` under `docs/contributing/capabilities/`, and a valid rule shape.
3. Add `apps/cli/src/doctor/rules.ts`, the rule evaluators. List files once with `git ls-files -z` and pass the list to every rule. Use `Bun.Glob` for matching.
4. Add `apps/cli/src/doctor/detect.ts`: `detect(root, registry, {remote:false})` returns `{id, status, evidence: Array<string>}`. The evidence is the matched paths or rule labels.
5. Add `docs/contributing/capabilities/registry.yaml` with three entries (`root_agents_md`, `codeowners`, `codeql_sast`) to prove the engine. CL-009 adds the rest.
6. Add `docs/contributing/capabilities/registry.yaml` to `tools/guardrail-files.json` and CODEOWNERS.
7. Tests: one per rule kind against a `gitRepo` fixture, the present, partial and missing combinations, and an untracked file not counting.
