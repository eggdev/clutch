# CL-039: Push releases with a GitHub App token so main can be protected

## Goal

The release job can push its release commit to a protected `main`, and a refused push leaves no orphan tag.

## Context

`release.yml` pushes `chore(release): vX.Y.Z` and the tag straight to `main` with the default Actions token. CL-106 protects `main` with a ruleset, and the default token cannot be on a ruleset's bypass list. On 2026-10-30 Brendan chose a GitHub App token over a release PR, which would double the PRs per merge.

## Steps

1. `release.yml`: when the `CLUTCH_APP_ID` variable is set, mint a token with `actions/create-github-app-token` from `CLUTCH_APP_PRIVATE_KEY`, and check out with it. Otherwise keep the default token.
2. Push with `git push --atomic`, so a refused `main` push also refuses the tag.
3. `gardening.yml`: open the gardening PR with the same bot token, so CI and agent review run on it.
4. Document the bot setup in `docs/contributing/setup/releases.md#the-release-bot`.

## Files

- `.github/workflows/release.yml`, `.github/workflows/gardening.yml`
- `docs/contributing/setup/releases.md`

## Acceptance criteria

- Without the variable, the next release still publishes with the default token.
- After Brendan creates the app (Gate), a release pushes to `main` with the bot token.

## Gate

Brendan creates and installs the app, then sets the variable and the secret. CL-106 adds the app to the `main` ruleset's bypass list.

## Verify

```sh
mise exec -- bun run validate
gh run list --workflow release.yml --limit 1
```
