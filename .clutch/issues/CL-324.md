# CL-324: Run the ticket driver on a timer and wake a thread that stopped

## Goal

A phase never stays `in_progress` with nobody working on it, and no ticket waits for a write command before its thread starts.

## Context

The driver of CL-318 runs only after a command that writes. When a thread dies, its phase stays `in_progress` and nothing sees it. OpenAI Symphony and Gas Town both run a loop that checks the tracker again and again and restarts a dead agent. The owner approved the same idea on 2026-11-21, in this form.

### The timer

- A systemd user timer runs every 2 minutes. It uses no agent run, so it spends no model tokens. Local CI runs on the machine the same way.
- The service reads a list of project checkouts from `~/.config/clutch/projects.yaml`. In each one it runs the project's own `clutch tickets dispatch`.
- `clutch tickets timer install` writes the two unit files to `~/.config/systemd/user/` and starts the timer. `clutch tickets timer status` prints the state of the timer and the time of the last run.
- The output of the service goes to `~/.local/state/clutch/timer.log`. The nightly backup covers that folder.

### The check

Each dispatch does one more job after it starts the ready phases. For each phase that is `in_progress`, has a thread, and has `advance: agent` in the phase file:

1. Read the state of the thread with `t3 thread show --json <thread>`.
2. The thread runs, is queued, or waits for an answer from the owner: do nothing.
3. The thread stopped, and the phase started or was last woken more than 5 minutes ago: send one message with `t3 thread send`. The message says that the phase is not finished, and tells the agent to continue or to set the phase to `blocked` with a reason.
4. The thread stopped again after 2 such messages: set the phase to `blocked`, with the reason "The thread stopped 3 times before the phase ended".

A phase with `advance: owner` is a conversation with the owner. Its thread stops after each question, so the check never wakes it.

The phase row gets a `wakes` count and a `woken_at` time. A change of status sets the count back to 0. Each wake and each block writes one line to `dispatch.jsonl`, and an event.

## Steps

1. Branch `clutch/cl-324-ticket-heartbeat`.
2. Add `wakes` and `woken_at` to the phase rows, with a migration of the store from version 2. CL-319a makes version 2.
3. Add the check to `apps/cli/src/tickets/dispatch.ts`.
4. Add `tickets timer install` and `tickets timer status`, and the reader of `~/.config/clutch/projects.yaml`.
5. Test the check with a fake `t3` command on the path.
6. Document the timer in `.clutch/README.md` and in the setup docs.
7. Hand test on the machine: install the timer, stop a work thread by hand, and see one wake message.

## Acceptance criteria

- With a fake `t3` that reports a stopped thread, a dispatch sends one wake message, and a second dispatch in the next 5 minutes sends none.
- After 2 wake messages and a third stop, the phase is `blocked` with the reason, and its work thread slot is free.
- A thread that runs, or that waits for the owner, gets no message.
- A phase with `advance: owner` gets no message.
- A store of version 2 opens after the change, and its rows have a `wakes` count of 0.
- `tickets timer install` on the machine gives an active timer, and `tickets timer status` prints the last run.
