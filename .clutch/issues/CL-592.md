# CL-592: Move the sender past its accepted event, and fix the small sync findings

## Goal

An accepted transaction always stops waiting on its device. A pull names its actor before it sends any record. An eager group that the actor gains on an open socket loads at once. The clients of a server that comes back do not all pull at the same moment.

## Context

The review of 2026-11-20 found four small faults in `packages/sync`:

- A command that writes only to a group that the client did not load gives the client no delta. The client's sync position moves only on deltas that it sees, so in a quiet organization it never passes the accepted event, and the transaction waits with no end.
- At sync ID 0, and for an eager group that the client did not name, `Page` messages came before the first `Groups` message, and only that message names the actor (CL-919). The pages of a new actor went into the saved copy of the last one before the pool could drop it.
- `feed.ts` asked access again after a change in the user's own group, and removed each lost group, but did not add an eager group that the actor gained.
- `retryWait` in `transport.ts` grew to 3 seconds and never shrank, and each client waited the same time.

## Steps

1. Branch `clutch/cl-592-sender-position`, stacked on CL-591.
2. Write the tests first: a transaction into a group that the client did not load stops waiting, over the real socket; the feed sends the empty delta, the gained group and the actor before the first page; the wait starts again after a pull that heard the server.
3. `Push` puts each accepted sync ID in a queue of the `Pull` of the same RPC client. The feed sends an empty delta at that sync ID once it sent each event before it, when no delta took the client there.
4. Before the first page of a pull, the feed sends a `Groups` message with the actor and the groups that have no page to come.
5. After a change in the user's own group, the feed loads each eager group that the actor gained, with its snapshot.
6. The wait before a pull or a push tries again gets a random part, and starts again from 200 ms after a pull that heard the server. CL-921 is the root fix.

## Acceptance criteria

- A transaction into a group that the client did not load stops waiting, over the real socket.
- Only the sender gets the empty delta.
- The first message of each pull names the actor, before any page. A group counts as loaded only after its last page.
- An eager group that the actor gains on an open socket loads with its snapshot.
- After a pull that heard the server, the next wait is near 200 ms again. Each wait has a random part.
