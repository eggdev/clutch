# CL-446: Run a council product review on each feature before it merges

## Goal

Each feature passes a council product review before it merges. 2 or 3 models from different providers score it 1-10 on a fixed metric set, against a rubric with anchors. Tools set the measured scores, and models judge only what a tool cannot measure. A feature merges only when every floor passes and no metric median is below 5.

## Context

- Brendan, 2026-11-06: "We should always have a part of our review process be a council review looking at how well our feature stacks up against our competitors on a scale of 1-10, against our performance, our clicks to completion, our information collected value, and more metrics I'll likely grow... we want to be highly critical of the implementations of agents."
- The council skill lives only in the owner's global skills (`~/.claude/skills/council/SKILL.md`). It gives a score out of 10, with no rubric, no anchors and no competitor input. Projects built by other people do not have it.
- Agent review (`docs/contributing/agent-review.md`) uses one provider, and judges the diff, not the product.
- Research, 2026-11-06. The metric set, ranked. M = a tool measures it, J = a model judges it.

| #   | Metric                                                                    | M/J | Merge floor                                                               | Clutch today                                    |
| --- | ------------------------------------------------------------------------- | --- | ------------------------------------------------------------------------- | ----------------------------------------------- |
| 1   | Task success                                                              | M   | A platform fails                                                          | `docs/principles/proof-gates-code.md`           |
| 2   | Interaction cost (clicks, keys, screens, KLM time)                        | M   | Over the journey budget or over `main`                                    | Sign-up budget only                             |
| 3   | Data value (each field has a reader, autofill, a reason)                  | M+J | A field no code reads, or a value asked twice                             | None                                            |
| 4   | Responsiveness (INP, long tasks, CLS, median of 5)                        | M   | The budgets in `docs/contributing/architecture/client-performance.md`     | Budgets exist                                   |
| 5   | Accessibility (axe, keyboard path, tree order)                            | M+J | An axe `serious` or `critical`, or no keyboard path                       | `docs/contributing/capabilities/a11y-checks.md` |
| 6   | Error recovery (bad input, offline, double submit, back, expired session) | M+J | Data loss, a dead end, or a generic message                               | None                                            |
| 7   | State coverage (loading, empty, error, partial, long, offline)            | J   | A blank or unstyled state                                                 | Proposal spec only                              |
| 8   | Clarity and trust (one primary action, cost before commit, undo)          | J   | A hidden cost, or no undo or confirmation on a step that cannot be undone | None                                            |
| 9   | Time to value (first screen to activation)                                | M   | Over the budget in project intent                                         | None                                            |
| 10  | Competitive standing                                                      | M+J | Worse than the competitor median on 2 or 9 with no owner reason (CL-447)  | None                                            |
| 11  | Craft and spec fidelity                                                   | J   | Visual review says `broken`                                               | `docs/contributing/agent-review.md`             |

- Calibration rules from the research:
  - Tools map a measured delta to a score with a fixed formula.
  - A judged score cites its evidence before the number. A score with no citation is `no score`.
  - The owner freezes 2 or 3 anchor features with agreed scores, which every prompt includes.
  - A 10 needs proof that no defect exists, and a lead over the best competitor.
  - Round 1 is blind. The implementer's model family takes at most one seat.
  - A floor metric takes the minimum score, and any other metric takes the median. A spread of 3 or more gets one exchange of evidence, then the lower score stands.
  - Score the anchors again after each model upgrade and every 20 PRs. Fix the rubric when a model drifts by more than 1 point, or averages above 8.5.
- Excluded: SUS, SEQ and HEART "Happiness". Their benchmarks come from real people, and a model playing a user does not produce a valid score.
- Sources: Google HEART, NN/g heuristics and error-message guidelines, Baymard checkout fields, the GDPR data-minimization rule, WCAG 2.2, web.dev INP, Prometheus and PoLL for judge calibration, and UICrit for few-shot UI critique.

## Steps

1. Move the council skill into `.agents/skills/council/`, so every project syncs it. Resolve providers through T3's `orchestrator_capabilities`, with the harness's subagents as the fallback. Report a missing provider, and do not swap in another.
2. Add `references/product-rubric.md`: the metric set, the 10, 7 and 4 anchors for each metric, the floors, and the calibration rules.
3. Make the journey runner write the measured metrics for each journey: clicks, keys, screens, KLM time, INP, CLS, long tasks, axe results and the field list. Each delegate gets one JSON file of these.
4. Add forced-error steps (metric 6) and a field-to-reader map (metric 3) to the journey templates of CL-440.
5. Run the council in `deliver` before `pr merge`, for each change that the design-proposal skill would cover. Put the score table in the PR body, and have the judge hold a PR that misses a floor.
6. Make kickoff ask the owner, in a T3 thread, for the anchor features and their scores.

## Acceptance criteria

- A feature PR carries a council table of all 11 metrics. Each judged score cites its evidence.
- A PR with a field that no code reads holds, and names the field.
- A PR whose metric median is below 5 holds.
- `bun run validate` passes.

## Verify

`mise exec -- bun run validate`, and a council run on a scratch feature with an unused form field. The run should report a metric 3 floor failure.
